# Fieldguide 项目介绍

> 一份完整的项目说明：要解决什么问题、怎么做的、做到了什么程度、证据在哪、边界在哪。
> 所有数字都由仓库内的命令生成或可复现，采集口径见每节末尾的"证据"。

---

## 一、一句话定位

**Fieldguide 是一个面向陌生代码库的本地学习工作台**：把仓库变成可导航的知识图谱与导览，
用「图谱约束的检索增强问答」回答问题，再把理解产物沉淀成可复习、可带走的个人知识。

技术主线是一句话可以验证的：**把大模型的问答从"文本相似度检索"升级为"结构约束 + 词汇桥接的检索增强"**，
并且把这个升级的收益用离线可复现的基准测出来。

## 二、要解决的问题

| 痛点 | 现有工具的问题 | 本项目的回答 |
|---|---|---|
| 工程侧：clone 完不知从哪读 | IDE 只有跳转、没有全局叙事；通用聊天没有持久项目结构 | 知识图谱 + 架构分层 + 引导 Tour + 节点↔源码联动 |
| 理论侧：论文与实现之间是鸿沟 | 论文归论文、代码归代码 | 论文 RAG + 概念桥接（段落 ↔ 节点）+ 自动生成对照 Tour |
| 理解侧：AI 会写代码，人要会判断 | 通用问答只解释片段，答完即忘 | 图约束的问答教练 + 进度 / 笔记 / 间隔复习 / 导师提问 |

## 三、功能全景（按用户旅程）

**看得见 → 问得清 → 记得住 → 带得走**

| 旅程 | 能力 |
|---|---|
| 看得见 | 项目库（本地/Git/内置 Demo）、代码地图 12 面板（总览 / 图谱 / 代码 / 问答 / 导览 / 知识 / 面试 / 探索 / 进度 / 笔记 / 导师 / Vault）、分屏与布局预设、全库内容搜索（Ctrl+Shift+F）、命令面板（Ctrl+K） |
| 问得清 | 学习教练（ReAct + 上下文装配 + 13 个工具 + **流式输出 + 可中止**）、探索面板（邻居 / 统计 / 两点路径）、洞察面板（技术债 / 演化时间轴 / 模块簇 / AI 审查） |

## 四、架构

```
   用户
    |
    v
+---------------------+   postMessage（15 下行 / 3 上行）   +------------------+
|  Fieldguide 壳       | <-------------------------------> |  UA Dashboard    |
|  Electron + React   |        ua-dashboard:// 协议        |  图谱渲染         |
|                     |                                    +------------------+
|  项目库 / 代码地图    |
|  学习教练 / 学习闭环  |        @understand-anything/core
|  论文 / 桥接 / 设置   |          （索引流水线）
+---------------------+                                    +------------------+
      |            |                                        |  项目目录         |
      | SQLite     |  单向导出（可选）                        |  .understand-    |
      v            v                                        |  anything/*.json |
  %APPDATA%    Obsidian vault                              +------------------+
  /Fieldguide    （外部落点，直接写文件）
```

- **技术栈**：Electron 33 + React 18 + TypeScript 5.7 + Tailwind + better-sqlite3 + electron-vite / electron-builder（NSIS）。
- **三进程模型**：main / preload / renderer；`contextIsolation: true`、`nodeIntegration: false`，
  renderer 只能调用 preload 手写白名单里的 API（**108 个通道一一对应，无孤儿、无通用透传**）。
- **图谱权威源**：项目目录下的 `.understand-anything/knowledge-graph.json`（就地索引，不复制源码、不写进数据库）。
- **学习数据**：SQLite（17 张表 / 9 条索引 / schema v5），只存 Fieldguide 自己的数据。
- **上游边界**：Tree-sitter 解析、多 Agent 索引、图谱画布全部复用
  [Understand-Anything](https://github.com/Egonex-AI/Understand-Anything)（MIT，commit pin）；
  本项目的贡献在集成层之上的问答、学习、导出与评测。

**刻意的硬约束**（写进文档、也写进实现）：不自研 parser / FileAnalyzer、不把图谱节点写进 SQLite、
不自建图谱画布、不改上游一行代码。

## 五、关键技术点

### 1. 图谱约束的上下文装配（context-first ReAct）

每轮对话**先装配上下文再进循环**：项目身份 → 架构分层 → 引导 Tour → 当前焦点节点 →
查询相关的图谱切片 → 论文与桥接，预算 10k 字符，最多 6 轮工具调用（末轮从协议层禁止调用工具强制收口），
并对「同工具同参数」去重。

### 2. 检索：从"语言敏感"到"语言无关"（本项目的核心改进）

**问题（实测）**：纯语义检索引擎在英文摘要的仓库上回答中文提问只有 **12.8%** Recall@5，
而同一套代码回答关键词提问有 68.0%。定位到两个原因：

1. **分词**：中文没有空格，「整句 = 一个词」的假设让词法通道对中文完全失效；
2. **词汇表**：中文提问说的是概念（入口 / 缓存 / 背压），索引里存的是标识符与英文摘要。

**方法**（`src/main/ua/lexical.ts`，纯函数、可单测）：

- **CJK 字符二元分词 + 标识符拆词**（`ErrQueueFull` → `err/queue/full`）；
- **中英术语映射**（73 条人工维护，把中文概念扩成索引里真实出现的英文词，权重 0.5 低于查询自身的词）；
- **BM25 打分** + **RRF 名次融合**（两通道分数不可比，按名次融合而不是调分）。

**结果**（离线基准，`pnpm eval:agent`）：

| 数据集（索引语言） | 提问形式 | 纯语义 | 混合检索 | 差值 |
|---|---|---|---|---|
| pulsegate（英文索引） | 中文自然语言 | 12.8% | **42.9%** | +30.1 pp |
| pulsegate（英文索引） | 关键词 | 68.0% | **70.2%** | +2.2 pp（不退化） |
| tiny-go（中文索引） | 中文自然语言 | 29.6% | **89.2%** | +59.6 pp |

产品里这条路径已经是默认行为（搜索徽标会显示"混合检索"或"词法检索（语义引擎不可用）"），
Agent 的搜索工具走的是同一实现——**基准测的就是产品在跑的那条路**。

### 3. 学习闭环与"带得走"的所有权模型

- 渐进四阶段（结构 → 架构 → 知识 → 面试），**没有 API Key 时全部走启发式兜底**；
- 间隔重复用 SM-2 lite（ease 1.3–3.0、间隔上限 3 年）；
- **Obsidian 单向导出**：正文写在 `%% fieldguide:begin/end %%` 托管块内，**块外用户批注与自定义
  frontmatter 逐行保留**；dry-run 与实际写入共用同一份计划；记账表只存路径与内容哈希；
  冲突三选一（保留我的 / 覆盖托管块 / 另存副本）；**二次同步 0 写入**，清理只删未被改动的文件。

### 4. 索引任务中心与"部分结果"

`index_jobs` 记录每次运行的模式、阶段结果、节点数与错误；
每个阶段（scan / parse / build / llm / save）都上报 `ok | skipped | failed` 与耗时，
**LLM 富化失败不再让整次索引失败**——结构图照样保存，界面显示"部分完成（摘要阶段失败）"并提供重试。

### 5. 流式对话与可中止

SSE 流式输出（跨网络分片的行缓冲、工具调用参数分片合并）、**用户停止按钮**、
**整轮 5 分钟截止时间**（原先后台最坏情况 6 轮 × 3 次重试 × 90s 无上限）。
一个刻意的语义：**一旦文字已经流到读者眼前就不再重试**——重试会把读者已经看过的内容再说一遍。

### 6. 工程质量与可验证性

- **契约三处同步**（main / preload / renderer 类型）+ 静态契约审计脚本（5 组检查）；
- **API Key 加密落盘**（safeStorage）、路径越界防护（拒绝绝对路径 / `..` / NUL）、
  原子写（temp+rename）与写后校验；
- **评测与文档同源**：`docs/eval/*.md` 全部由命令生成，禁止手改数字。

## 六、评测与数据（可复现）

| 项 | 命令 | 结果 |
|---|---|---|
| 检索 / 消融基准 | `pnpm eval:agent` | 2 个仓库 / 34 题 × 7 检索模式 × 3 提问形式 × k∈{5,10}，**84 个变体** |
| 答案级指标（引用忠实度 / 精确率 / 召回率 / 幻觉率） | `pnpm eval:record-answers` → `pnpm eval:answers` | 录制需 Key（唯一花钱步骤），**评分离线可复现** |
| 单元测试 | `pnpm test:unit` | **50 个文件 / 498 通过 / 2 skipped** |
| 端到端 | `pnpm test:e2e` | **4 个文件 / 19 例**（真实 Electron 二进制） |
| 基线套件 | `pnpm qa:baseline` | typecheck + 单测 + fixture 图 + 契约审计 |
| 大项目冒烟 | `pnpm qa:his-go` | 3656 节点的真实 Go 项目 |

**基准里最值得说的三条结论**：

1. 检索是决定性的：无检索基线 **0%**；
2. 语言敏感性可以在**检索层**修复（不是模型能力问题）——见上表；
3. 两个"负结果"如实记录：邻居扩展在 pulsegate 上零增益、在 tiny-go 上有增益（依赖图规模与索引语言）；
   中文档仍低于英文档，瓶颈是术语映射的覆盖率。

## 八、边界与已知局限（主动交底）

1. **安全模型是"进程隔离 + 最小暴露面"，不是 Chromium 沙箱**（`sandbox: false`）；
2. IPC 入参校验是**手写守卫**，没有运行时 schema 库，一致性靠静态审计脚本；
3. **中文检索仍弱于英文/关键词**，术语映射是人工维护的覆盖瓶颈；
4. 原子写**没有 `fsync`**（崩溃一致性 ≠ 掉电持久性）；
5. 图谱增量用 **mtime 水位线 + 在场集合**（不是内容哈希），文件改名会静默断掉跨文件边；
6. 论文向量检索是**暴力余弦**（无 ANN，`paper_chunks` 全表 + JS 计算）；
7. embedding 调用**未计入 token 计量**，成本章节只覆盖对话侧；
8. 覆盖率统计**有意图但无门禁**（未设阈值）；
9. `qa:his-go` 依赖仓库外的兄弟目录，不是可移植门禁；E2E 未进 CI（CI 无法构建 Dashboard 产物）；
10. **真人用户研究尚未执行**：协议、量表与计分代码齐备（`docs/eval/user-study-protocol.md`、
    `src/main/eval/usability.ts`），但数据必须由真实参与者产生，仓库里不预置任何模拟结果。

```bash
git clone https://github.com/Tangyd893/Fieldguide.git
cd Fieldguide
pnpm bootstrap:ua     # 准备图谱引擎（clone 上游并构建 Dashboard）
pnpm install
pnpm dev              # 首次启动有引导向导；没有 API Key 也能用结构图与学习闭环
```

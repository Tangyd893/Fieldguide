# Fieldguide 差异化架构提案：从「12 个并列面板」到「一个引擎 + 三个出口」

> 版本：v1.8（2026-09-20）| 状态：**待评审**（未修改任何产品代码）
> 起因：产品经理反馈「功能太单一太普通，没有吸引用户的能力」
> 结论：**PM 的体感成立，但归因不成立。** 功能数量不是瓶颈（12 个面板 / 103 个 IPC / 13 个 Agent 工具 / 3 语 / 学习闭环 B1–B9 已全部落地）；瓶颈是**能力并列不成主线、旗舰能力实际是假的、产物走不出本机**。
> 而独立调研给出更不留情的事实：**Fieldguide 的五个支柱已被免费产品覆盖**（graphify 116–120k★，连 Obsidian 导出与 arXiv 桥接都有），**它选的品类作为独立生意已被证伪**（CodeSee 用同样话术标价 $29–69/月，品牌已被 GitKraken 吸收），**而"气隙本地优先"这个位置已被 graphify 的 YC 母公司用同样措辞占住**。
> 唯一未被占据的位置是 **"证明人读懂了变更"（而非"证明代码没坏"）**——有 Lacy/FSE 2026 的唯一实验支撑（专家策展 Tour **83% vs 57%**），但**无需求证据、免费侧已有 0★ 先例**；而更值得先做的是 §1.8 那条**确定性**目标：**没有任何工具同时做到"锚定 + 稳定 + 谁在何时确认"**（竞品自己承认把核对工作交给了读者）。
> 本文给出：诊断（§一，含竞品与学术证据）→ 解决方案（§二）→ 可行性分析（§三，含商业定位的诚实结论）→ 明确不做（§四）→ 需拍板事项（§五）

## 一、诊断：把「太普通」翻译成可修的工程问题

### 1.1 先核对事实：这个项目并不「功能单一」

| 维度 | 实测 | 证据 |
|------|------|------|

**所以「功能太少」这个归因是错的。** 若按此归因追加功能，等于在已经 32,131 行、12 个面板的基础上再加 5 个面板——**这条药方已经被执行过了**：`gap-analysis` 提议的「学习闭环（B1–B9）+ 可验证性（C1–C3）」这一整轮就是「补齐功能点与体系」，**全部交付完成后 PM 的抱怨依然到来**。这本身就是「加功能无法解决吸引力问题」的实验证据。

### 1.2 真实病症（六条，每条带证据）

#### D1 · 能力是「并列」的，不是「递进」的 —— 体感「普通」

12 个面板彼此独立、地位平等，用户打开后面对的是一个**工具箱**而不是一条**路径**。产品动词以「看 / 读」为主（图谱、代码、Tour、知识卡），缺少「测 / 评 / 交付」类动词。

- `docs/gap-analysis-and-feature-roadmap.md:18` 早已点破：「产品的动词只有『看』，没有『记 / 练 / 评 / 进』」——Phase 6 补了「记 / 练」，**「评」与「交付」仍是空的**。
- 结构性证据：任何一层都不为下一层提供输入。读过图谱不产生进度数据，进度不产生复习，复习不产生可交付物。**没有复利，所以看不到「越用越强」**——这正是「普通」的观感来源。

#### D2 · 旗舰能力实际是假的 —— 体感「不吸引人」的直接来源（**最致命**）

产品把「语义代码搜索」当作已交付能力：

- `docs/doc-index.md:94` 功能归属矩阵写着：`语义代码搜索 | UA ✅ | Fieldguide 包装 IPC（可选）`
- `docs/eval/agent-baseline.md:20` 把该通道称为「语义检索」，并据此得出「语义引擎优于子串」的结论。

**但代码里的实现是 Fuse.js 模糊字符串匹配，没有任何向量：**

```
src/main/ua/search.ts:2      * UA-backed node search — ... degrades to a deterministic substring matcher
```

- 上游 `SearchEngine` 的实现（`Understand-Anything/.../core/src/search.ts:2,14-25,46`）：`new Fuse(nodes, FUSE_OPTIONS)`，`threshold: 0.4`，`keys` 为 name/tags/summary/languageNotes；查询按空格切成 `"a | b"` 做 extended search（`:46`）。
- 上游**其实提供了**真正的向量引擎 `SemanticSearchEngine` + `cosineSimilarity`（`core/src/embedding-search.ts:14,37-78`，并从 `index.ts:17` 导出），**Fieldguide 从未接线**（全仓无引用，`src/main/ua/search.ts` 只用 `SearchEngine`）。

**最有力的一条证据来自代码自己的注释**（`src/renderer/views/CodeMap/NodeSearchBar.tsx:4-8`）：

> Phase 2.5 originally did client-side `label.includes()` over a full `graph:get` payload (**a "fake" semantic search**). It now calls `graph:search` with an explicit mode: `semantic` runs **the UA SearchEngine** in the main process (falling back to a deterministic substring matcher)…

**翻译**：团队**曾经发现并记录过「假语义搜索」这个问题**，然后把它「修复」为调用 UA `SearchEngine`——而 UA `SearchEngine` 的实现就是 Fuse.js 模糊字符串匹配。**问题被识别了，却用一个同样不具备语义能力的实现对冲掉了，并在注释与 UI 层面继续把它称作 `semantic`。**

这说明 D2 不是疏忽，而是**团队对该能力的「真/假」缺乏可判定的标准**——这正是 `capability.ts`（能力协商）要解决的：一个能力能不能叫「语义」，必须由**实测指标**判定，不能由「我调用了上游的那个类」判定。

**完整证据链（这个问题被识别过、也被宣布修好过，但仍然存在）**：

| 层次 | 文档/代码说了什么 | 实际情况 |
|------|------------------|----------|
| ① 能力归属 | `doc-index.md:94`「语义代码搜索｜UA ✅｜Fieldguide 包装 IPC」 | 记为已交付 |
| ② 审计识别 | `gap-analysis:162` 明确写下：「文档宣称的"语义搜索"是**假语义**」 | **问题已被识别并记录** |
| ③ 宣布修复 | `gap-analysis` §3 进度注：**「语义搜索已真做」**；A14 标题「把"假语义搜索"变成真语义」（`:220`） | A14 实际交付的是：`searchNodesDetailed()` **如实报告后端** + `NodeSearchBar` 改服务端防抖搜索 + 支持 `mode`/`limit` |
| ④ 真实现状 | 被"升级"为语义引擎的那个类，就是 **Fuse.js**（`core/src/search.ts:14-25`） | **引擎未变**：A14 交付了「诚实的标签」，没有交付「语义」 |

**结论**：A14 是一次**指标口径修复被误当成能力修复**的典型。它让后端变得诚实（这一步很有价值，也是我提议保留 `backend` 字段的原因），但**没有人验证指标是否真的提升**——而中文指标实际是下降的（见下）。这类问题不靠更努力就能避免，靠的是**把「能力是否可用」变成可判定、可回归的断言**。

**后果是可量化的，且正好打在产品首发画像上：**

| 提问形式 | Recall@5 | MRR | 说明 |
|---------|---------:|----:|------|
| 关键词 | **68.0%** | 0.820 | 用户输入英文标识符 → 能用 |
| 英文自然语言 | 26.4% | 0.433 | 明显变差 |
| **中文自然语言** | **12.8%** | 0.240 | **首发 locale（`config.ts:135` 默认 `zh-CN`）下的主用法** |

（数据：`docs/eval/agent-baseline.md:6-21`、`:46-54`）

> **本次已实跑复现**：`pnpm eval:agent`（离线，无需 API Key）在 3 秒内重跑 24 个变体，逐项复现上表（语义检索 / 中文 @5 = 12.8%、关键词 @5 = 68.0%），并**逐字节重写了 `docs/eval/agent-baseline.md`（`git diff` 为空）**——评测的可复现性成立，因此它可以作为回归门禁进 CI。

**另一个此前未被注意到的回归**：把 Recall@10 一并看，中文场景下「语义检索」**比纯子串匹配更差**——

| 中文自然语言 | Recall@5 | Recall@10 |
|-------------|---------:|----------:|
| 子串匹配（旧实现） | 11.8% | **21.6%** |
| 语义检索（`semantic` 模式，即 UA Fuse） | 12.8% | **12.8%** |

@10 与 @5 完全相同，意味着**该通道在中文下总共只召回 12.8%**，而它所「替代」的子串实现能召回 21.6%。也就是说：`NodeSearchBar.tsx:4-8` 注释里那次「从 fake semantic 升级到 UA SearchEngine」的改动，**对中文用户而言是一次召回能力下降**。这正是「没有可判定标准」的代价——升级时没有人看中文指标。

机制上完全可解释：中文整句按空格切分后作为一个超长 term 交给 Fuse 做模糊匹配，节点正文（英文标识符 + 英文摘要 + 文件路径）几乎不可能命中；12.8% 的召回基本来自句中偶然夹带的英文 token（如 `HTTP`）。**中文用户第一次问「认证逻辑在哪」就可能拿到空结果或一堆无关节点。**

对照 `docs/doc-index.md:182` 的产品验收标准——「搜索/聊天能答「X 在哪」并一键跳节点」——**该验收项在默认 locale 下事实上不成立**。

这是「没有吸引用户的能力」最直接、最可修的来源：不是缺功能，是**旗舰功能名不副实**。

#### D3 · 产物走不出本机 —— 体感「没吸引力」的增长侧

当前所有价值都锁在应用内：产物 = 应用内面板 + `<appData>/exports/` 的 Markdown（`src/main/insights.ts:166`）+ 需先有 vault 的 Obsidian 卡片（`src/main/obsidian/cards.ts:368`）。

- 没有**无需安装即可打开**的产物 → 用户无法把「我读懂了 X 项目」递给任何人（同事 / 面试官 / 博客读者）。
- 没有分发回路 → 每个用户都是终点而不是渠道，自然增长为 0。

#### D4 · 可信度不可见 —— 体感「和 ChatGPT 没区别」

项目真正的技术资产是**图谱锚定 + 引用溯源 + 离线评测**（`metrics.ts:1-15` 的引用精确率 / 忠实度 / 幻觉率家族），但用户界面里看不到「这次回答有多少比例锚定在真实节点上」。

对比通用 ChatGPT 时，用户感知不到差别 → 判为「普通」。**能力差异存在，但没有被外化成用户看得见的一行数字。**

#### D5 · 缺少「能力探测与降级」层 —— **D2 的同源第二例**（本次审计新发现）

D2 不是孤立事故。审计中在同一根因下找到第二例：

**论文 RAG 在默认供应商配置下同样是坏的。**

| 环节 | 事实 | 证据 |
|------|------|------|
| 本机实际配置（即默认形态） | `baseUrl=https://api.deepseek.com/v1`、`embedModel` **为空** | `%APPDATA%/Fieldguide/config.json`；默认值 `src/main/config.ts:133`（`embedModel: ''`） |
| 内置目录是否撒谎 | **没有**。DeepSeek 的 `embedModels: []` 是诚实的 | `src/shared/llm-catalog.ts:30` |
| 实测 DeepSeek 能力 | `GET /v1/models` 只返回 **2 个 chat 模型**（`deepseek-flash`、`deepseek-v4-pro`）；`POST /v1/embeddings` → **HTTP 404 NotFound** | 本次实测（2026-09-20，真实 Key 探测） |
| 但 `embed.ts` 的行为 | `embedModel` 为空时**静默编造** `'text-embedding-3-small'`，再发往 DeepSeek 的 `/v1/embeddings` | `src/main/vector/embed.ts:30,77` |
| 后果 | 论文建立索引 → 404 抛错。**「论文 RAG 全链路复活」（`gap-analysis §3 A1 ✅`）在 DeepSeek 这种最常见的中文用户配置下不成立** | `vector/index.ts:111` |

**根因（两例共享）**：产品把「能力」当作理所当然存在（多语言语义匹配、embedding 端点），**既不在配置期校验，也不在运行期显式降级**——失败要么静默（D2 的假语义），要么以一句 404 抛出（D5）。

这解释了为什么文档上大量 ✅ 与用户体感严重背离：**验收是在「开发者自己的理想配置」下做的，而用户跑在默认配置上。**

> 这是本提案相对「再加功能」最本质的区别：D2/D5 都**不是缺功能**，缺的是**能力协商层**。不补这一层，加再多功能都会在默认配置下静默失效。

**D5 家族还有第三、四例（静默失败与"不可用而不告知"是模式，不是意外）**：

- **第三例**：`docs/OCR-report.md` 的 11 条建议中，**#8（`OverviewPanel` 对后端数据结构无运行时校验）与 #9（`KnowledgePanel` 用 `catch { /* ignore */ }` 静默丢弃错误，「用户看到空列表，完全不知道出了什么问题」）未被清理**——A16 只处理了「高价值项」（`todos.md:154-158`），这两条留在了原地。
- **第四例（换模型即坏）**：`vector/` 把向量以 **JSON 数组裸存 SQLite**，检索是**全表余弦扫描**，且**没有「换 embedding 模型后重新嵌入」的机制**（`vector/index.ts` 无按模型失效逻辑）。用户一旦在设置里更换供应商或 embedding 模型，旧向量与新查询向量维度不同，`cosineSimilarity` 会直接抛「Vector dimension mismatch」——**又是一次没有预防、没有提示、没有降级的能力变更**。

四例同一模式：**失败不发声**（假语义静默降级、embedModel 静默编造模型名、catch 静默吞错、换模型静默失效）。因此除 `capability.ts` 之外，本提案建议一条纪律：**任何降级或能力失效都必须在 UI 上有一处可见状态**（出口 C 的「检索后端」徽标是这条纪律的第一个实例；`NodeSearchBar` 已展示 backend 的做法证明了这条纪律在本仓可行）。

#### D6 · 工作台像「两个产品粘在一起」，且同一件事有 2–3 份实现

**审计给出确切数字**（详见附录 A）：

- **与内嵌 UA Dashboard 重影的 5 项能力**：CodeViewer / LearnPanel（进度）/ PathFinder / Onboarding / Shortcuts —— 壳层自己写一份（在 `src/`，可读可测），Dashboard 里各有一份（`resources/dashboard` 下 **2.6 MB minified 产物**，不可审计）。
- **同一件事多份实现**：节点搜索 **3 份**（`App.tsx:833-842` 命令面板前端 `includes`、`graph:search`、`tools.ts:155-171` 又手写一遍子串回退）；文件搜索 2 份；论文检索 2 份（`paper:search` 的 JS `includes` vs `paper:query` 的向量余弦）；最短路径 2 份（`graph-reader.findPath` 与 `InsightsPanel.tsx:662-715` 的 `breadthFirstPath` 复刻，注释自承 "mirroring `graph-reader.findPath`"）。
- **问答面有 4 个**：`ChatPanel`（完整教练）／`TheoryView` 内联教练（同一 `chatSend`，但无历史、无步骤、无引用）／`TutorPanel`（导师提问+评分）／`InterviewPanel`（面试演练）。
- **「测验读者」有 3 套独立功能栈 + 3 组数据表**：面试题（`interview_questions`）／导师提问（`coach-plus.ts`）／间隔复习（`review_cards` + `review_logs` + `srs.ts`）。

讽刺之处：README 的硬约束「**禁止**自研 parser / 独立图谱画布」**被严格遵守**，但同为硬约束精神的「不重复造轮子」在**功能层被违反 5 次**——`App.tsx:833-842` 用的正是 `NodeSearchBar.tsx:4-8` 注释里点名否定的那种写法。（注：Dashboard 是上游产物不可改；但上述重复**全部发生在壳层内部**，是自选的。）

**用户侧后果**：两个聊天入口、两个搜索框、两套代码视图、同一件事有两种做法——「有限选择、自由搭配」的产品原则（`product-spec.md:29`）在实现上退化为「选择过多」。**12 个面板 tab + 9 个布局预设，却只有最多 2 个可视窗格**（`SplitPanel.tsx:181-183`）。这直接喂养了 D1 的「工具箱」体感。

### 1.3 诊断结论

| PM 的说法 | 工程翻译 |
|-----------|----------|
| 功能太单一 | ❌ 不成立（12 面板 / 32.1k 行 / 学习闭环 B1–B9 与可验证性 C1–C3 已全部交付） |
| 功能太普通 | ✅ 成立 = **能力并列不成主线**（D1）+ **上手即两个产品**（D6） |
| 没有吸引用户的能力 | ✅ 成立 = **旗舰能力名不副实**（D2）+ **能力协商层缺失致默认配置静默失效**（D5）+ **产物不可传播**（D3）+ **可信度不可见**（D4） |

**一句话**：问题不在「功能少」，在「**宣称的能力与默认配置下真实可用的能力**之间没有约束」——D2 与 D5 是这个缺口的两处伤口，D1/D3/D4/D6 是它的体验后果。

因此解决方案的形态必须是：**收敛一条主干，让旗舰能力变成真的，把价值外化成用户能带走、能看见的东西**——而不是再加面板。

### 1.4 外部证据：这些病症正好落在市场最大的痛点上（**本条改变了方案优先级**）

以上诊断若只是内部整洁度问题，就不值得投入 9 周。独立的外部调研（一手取证，来源见下）显示：**D4 与 D2 命中的正是开发者工具市场当前排名第一的抱怨。**

| 外部证据 | 数字 | 对 Fieldguide 的含义 |
|----------|------|---------------------|
| **AI 工具「缺少我所在代码库的上下文」** —— Stack Overflow 2024 调查（n=30,661 / 专业开发者 24,496） | **63.3% / 64.6%** | 这正是 D4。Fieldguide 的技术资产（图谱锚定 + 引用溯源 + 忠实度指标）**就是为这句话准备的答案**，而现在用户在界面上看不到它 |
| **「不信任 AI 的输出或答案」** —— SO 2024（同上样本） | **66.2% / 66.1%** | 出口 C（可信度外化）不是「锦上添花的差异化」，而是**直接对着最大痛点** |
| **「AI 给的答案几乎对、但就是不对」** —— SO 2025（n=31,476，数据集字段 `AIFrustration`） | **65.98%**（排名第一的挫败感） | 「差一点对」的本质是**检索没命中正确节点**——即 D2。检索质量不是内部指标，是产品口碑 |
| **「很难理解代码为什么这么工作」** —— SO 2025（同上） | **16.32%** | 自报的「理解失败」度量 |
| **在用 AI「学习一个代码库」的比例 / 想用的比例** —— SO 2024（n=35,978） | **30.9% / 40.6%**（+9.7pt） | 这是一个**尚未被工具充分覆盖**的环节（对比：代码评审 +27.7pt、测试 +19.0pt）。见下「诚实边界」 |
| **程序理解占开发者时间** —— Xia et al., *IEEE TSE* 44:951–976, 2018（跨应用 HCI 埋点；7 个项目 / **78 名职业开发者 / 3,148 工时**） | **约 58%** | 问题的**规模**有一手同行评审证据支撑；且论文指出**资深开发者花在理解上的时间显著少于初级开发者** → 痛点集中在**新手/onboarding 群体**，正是 Fieldguide 的目标画像 |
| **AI 引入后资深开发者的负担** —— Xu et al., arXiv `2510.10165` | 核心开发者**评审量 +6.5%**、自身编码产出 **−19%** | AI 时代时间从「写」转向「读与评审」→ comprehension 需求**在上升**，方向利好 |
| **Onboarding 时长本身** —— SO 2024/2025 调查**没有**专门问题 | — | 这是一个**证据空白**：业界连 onboarding 成本都很少量化 → 出口 A（读懂度体检）若能给出可量化分数，本身就是稀缺品 |

**这改变了优先级判断**：原方案把出口 C（4 人日）视为附带项。依据上表，**出口 C 应提升为与 D2 并列的第一优先**——因为它是唯一能把「我们有图谱」翻译成「所以我们可信」的用户可见证据，而「不可信 / 缺上下文」是市场排名第一的抱怨。

### 1.5 定位错位：文档选定的差异化太窄（**这是「吸引不到用户」的策略层原因**）

文档对「我们和别人有什么不同」有明确答案，且是**不可漂移**的：

> `doc-index.md:15`：**Fieldguide 差异化？｜独立桌面、论文/PDF、概念桥接、跨论文+代码 Agent**
> `design-review.md:57`：「**桥接 = 把两边连起来的工作台（产品差异化核心）**」
> `design-review.md:213`：「最终差异化靠 **概念桥接 + 跨源 Agent + 桌面学习工作台体验**」

问题在于：**「论文 ↔ 代码桥接」服务的是一个交集很小的人群**——既要能读代码、又要读 arXiv 论文、且论文正好对应手上这个仓库。首发画像（`product-spec.md:40`「主动跟踪 GitHub 热门项目与 **arXiv**」）本身就承认了这是个小众设定。

与此同时，市场最大的痛点是**普遍性**的：

| | 概念桥接（文档选定的差异化） | 可信的代码库上下文（未被外化的差异化） |
|---|---|---|
| 受众 | 读 arXiv 且论文对应本仓库的人 —— **交集窄** | 所有用 AI 读/改别人代码的人 |
| 外部证据 | 无直接市场证据 | **64.6%** 说 AI 缺代码库上下文、**66.1%** 不信任其输出、**65.98%** 抱怨"几乎对但不对" |
| Fieldguide 是否已具备 | 已具备（`concept_links` + 对照 Tour） | **已具备但不可见**（图谱锚定 + 引用溯源 + 忠实度指标） |
| 竞品能否短期复制 | 难（确实独特） | 难（需要图谱 + 评测集 + 中文 pipeline） |

**结论（本提案的策略主张）**：文档选定的差异化是**功能级、窄受众**的；而「**可验证的图谱锚定**」是**痛点级、宽受众**的差异化，且**资产已经在手，只是没显示给用户**。

更要紧的是：概念桥接本身**也建在同一套检索地基上**（`query_paper` + 图谱检索），地基是裂的（D2）——**窄差异化与宽差异化共享同一个必须修的前提**。所以修检索主干不是「为了做新功能」，而是**同时解锁既有的窄差异化与潜在的宽差异化**。

> 对 PM 的直接含义：**"功能太普通"的部分真相是"我们选了一个只有少数人才需要的不同点"。** 不是加功能，是**把已有的独特能力指向更大的人群**。

### 1.6 竞品实况：五个支柱都已被免费产品覆盖（**本节最伤人也最重要**）

独立调研（一手取证：厂商页面 / GitHub / HN Algolia API / Wayback / Crossref / Semantic Scholar / **YC 官方目录**；**Reddit 全程 403，未采信**）给出的事实：

| Fieldguide 的支柱 | 是否还是差异化 | 竞品证据 |

| 代码库知识图谱 | ❌ 已商品化 | **graphify 116–120k★**（下详）；codegraph 71.8k★ MIT；`DeusData/codebase-memory-mcp` **44,144★**；GitNexus 47.5k★；`vercel-labs/lat.md` 1,986★；**GitHub 搜索 `codebase knowledge graph` 返回 542 个仓库** |

**即：Fieldguide 的"知识图谱 + arXiv 桥接 + Obsidian 同步"三件套，已被一个以 Claude Code / Cursor / Codex / Gemini CLI skill 形态分发的项目完整覆盖。**

按不可漂移的定义（`doc-index.md:15`「差异化 = 独立桌面、论文/PDF、概念桥接、跨源 Agent」）逐条核对，**只有"独立桌面形态"与"概念桥接的深度"还站得住**，而"论文/PDF"已被 graphify 的 arXiv 命令覆盖。

#### ⚠️ 1.6.1 重要更正：graphify 不是"免费无公司的开源项目"，而是一家 YC 公司

本节初稿（v1.1）把 graphify 描述为"免费、Apache-2.0、查无公司"，并据此推论"本品类的免费 OSS 不产生商业模式"。**这个推断是反的，必须更正**（已直接向 YC 目录核实）：

> **graphify 是 Graphify Labs 的开源楔子——Y Combinator Summer 2026（旧金山）**，其付费产品是 *"a Knowledge Graph **control plane** for enterprise software"*。YC 页面原文：
> *"The open-source tool has **116K+ GitHub stars and 6.5M+ downloads**, and is used in production by engineers at **Shopify, Datadog, JP Morgan, American Express, Harvey, Automation Anywhere, and Vanguard**. On top of that graph, our **enterprise layer reviews every pull request and formally verifies each code change: it proves the new behavior matches the old, or hands back the exact input that breaks it**… **It runs entirely inside your perimeter, fully air-gapped on-premise or self-hosted in your own cloud, so no code or data ever leaves your environment."**

创始人 Safi Shamsi（YC S26）：**~5 个月内 116K stars、6.5M+ PyPI 下载、头几周 6,000+ 平台注册**，被称为"YC 公司史上排名前五的开源项目之一"。

**四条后果，每一条都改写本文的结论**：

1. **正确的教训与初稿相反**：本品类跑通的打法是 **OSS 楔子 → 付费企业验证层（open-core）**，与 GitNexus 同形，且现在有了资金与规模的确认。**"免费竞品多所以没商业模式"是错的推论。**
2. **"气隙 / 本地优先"已不再是一个可占据的位置**——它正被一家 YC 公司用**几乎逐字的措辞**营销，而对方有 100k+ star 的分发引擎与财富 100 客户。**本文 §2.4 初稿说"可审计的零外发是一个空位"，这句话必须撤回：那不是空位，那是 graphify 的主场。**
3. **Graphify Labs 的企业楔子，正是调研独立推荐给 Fieldguide 的"AI 验证"定位。** 建议本身仍然成立，但**窗口正在关闭**，且 Fieldguide 会是资源远逊的**后进者**。
4. **他们的开场诊断与 Fieldguide 几乎同义**：*"no one can hold the whole codebase in their head, and no one can be sure an AI's change didn't quietly break something."* **——所以 Fieldguide 不需要去推销这个问题，它需要一个不同的答案。**

#### ⭐ 1.6.2 但两者证明的东西不同：**它验证机器，Fieldguide 可以验证人**

这是本次更正里唯一对 Fieldguide 有利、且我认为最有价值的区分：

| | **Graphify Labs 的企业层** | **Fieldguide 的出口 A/C** |
|---|---|---|
| 证明的命题 | "**新行为与旧行为等价**"（或交出让它失败的确切输入）——**对代码的形式化/行为验证** | "**某个具体的人读懂了这次变更**"——**对人的理解证据**（体检分数 + 出处 + 新鲜度） |
| 手段 | 图谱 + PR 自动审查 + 行为等价性证明 | 应用型体检题（Lacy 式）+ 生成/人工出处标注 + "验证于 commit X" |
| 买家 | 要"AI 生成的改动没悄悄破坏东西"的工程组织 | 要**合规 / 交接 / 审计**证据的组织（即 Understand by SciTools 的买家逻辑） |
| Lacy 证据支持 | 不适用 | **83% vs 57%**（专家策展 Tour 的测验分数） |

**结论**：不要和 Graphify 比"谁证明了代码没坏"——它用 AI + 形式验证，且资金、分发、客户名单都压倒性领先。**要比"谁能证明人读懂了这个变更"**：那是 Lacy 测量的东西，是合规买家的东西，而 **Graphify 明确不做**（它做的是行为等价性证明）。**这是 Fieldguide 在本次调研中唯一找到的、既未被占据又与自身资产吻合的位置。**

**更难看的两条市场事实**：

1. **CodeSee 卖的正是 Fieldguide 的话术，且它作为独立产品没有活下来**——codebase maps + "Interactive code tours" + 页面标题就是 "Codebase onboarding / offboarding"。历史标价 **Community $0 / Business $69 或 $29 每协作者每月**；**2024-05-14 被 GitKraken 收购**，`codesee.io` 在 2026-05 仍返回 200、**2026-06 变 301、2026-07 变 404**（`/pricing` 亦 404）。⚠️ **诚实修正**：其品牌与定价页已下线，但 `docs.codesee.io` 仍在线且无 EOL 公告，**GitKraken 至今仍在售名为 "Codemaps" 的产品**——因此"**正式日落 UNVERIFIED**"，只能说品牌被关掉、能力被吸收。CodeBoarding（同为架构视图）则把商业故事**转向 PR review**。
2. **本品类的"框架"本身在开发者社区不奏效**：HN 上同品类 Show HN 帖得分 **2–7 分、约 0 评论**——**包括 graphify 自己那一帖（2 分）**；它后来是靠**形似"另一个卖点"的东西（token 节省，"71.5× fewer tokens per query"）叠加 skill 形式分发**做到 116k★ 的。唯一突破的是**免费 + 零安装 + 公开**（DeepWiki 231 分，机制是 `github.com` → `deepwiki.com` 换域名即看）。最贴近 Fieldguide 的对标 **Doculearn** 用几乎逐字的同一句话（"AI 让我们写代码更快了，但需要理解'整个系统如何工作'"）**在 HN 发过四次，得分 2 / 1 / 1 / 1**。
3. ⚠️ **两个资金最充足的同类定位者都已经离开了这条赛道**（本节最该被记住的一条）：

| 公司 | 原定位 | 转向 | 出处 |
|------|--------|------|------|
| **CodeSee** | codebase maps + "Interactive code tours" + "Codebase onboarding"（**≈ Fieldguide 的原话**） | 2024-05 被 GitKraken 收购，品牌与定价页下线，能力被吸收为 "Codemaps" | §1.6.1 前文、SD Times / FinSMEs |
| **Swimm**（**已融资 $33.3M**，**就在 Fieldguide 的车道上**） | *"docs that don't lie"*（2023 年 **$390/月 / 25 座**，带"文档不撒谎"的验证测试） | **两次转向**：① → **"De-Risk Legacy Modernization"**，**服务主导**、围绕**主机（mainframe）**、以 **Assessment** 立项；② 并且**把知识库卖给 AI 而不是卖给人**——现行官网原文：*"Build the validated knowledge base **your AI tools need to understand your codebase. Copilot, Cursor, Claude Code, internal agents, MCP servers.**"*（页面 HTTP 200，已直接抓取） | Swimm 现行官网（一手） |

**含义**：**"把理解卖给人类开发者"这个定位，已经被两个拿到资金、且做得比 Fieldguide 更早更深的团队放弃过。** 这比我 v1.5 里"CodeSee 没活下来"单条证据重得多——**它不是一次失败，是一致的方向性撤离。**

**这给出了对 PM 那句话最诚实的翻译**：

> **不是"功能太单一太普通"，而是"选了一个开发者在公开场合不响应的品类，而这个品类的头部已经免费、其企业版已被 YC 资金押注"。**

**Fieldguide 还有一个结构性营销劣势**：竞品能把价值写进 README 徽章（"71.5× fewer tokens"、"99% fewer tokens"），**而"理解"无法放进一张基准表**。这正是出口 A 存在的根本理由——**体检分数是本产品唯一能变成可证明数字的东西**（见 §2.2 的 Lacy 证据）。

**诚实的边界**：HN 是自选择受众，会低估很多东西；star 与价格均为 2026-09 时点读数、逐日漂移；Reddit 数据缺失；GitHub 搜索的"542 个仓库"为报告值、未独立复跑（当次 API 限流）。**但"知识图谱"这个说法得分 2–4 分、零评论，且包含 116k★ 项目自己的帖子**——这个模式是稳定的。**另需记住一条方法论教训：链接可核验 ≠ 主张被覆盖（调研中有一个分支 9 条主张里有 4 条"链接通过、主张被丢弃"）——所以本文优先引用原文而非链接。**

### 1.7 学术与实测证据：**检索才是本品类的瓶颈**（这直接验证了本文的主干选择）

这一节把 D2 从"我们的一个 bug"升级为"**品类公认的核心缺陷，而我们有测量仪器**"：

| 证据 | 内容 | 对本文的意义 |
|------|------|-------------|
| **CodeRAG-Bench**（10 个检索器 × 10 个模型） | **"检索本身才是瓶颈"**；且输入越长性能越差（18 个模型）、长上下文中段信息利用最差 | **检索不是内部整洁度问题，是本品类测得的性能瓶颈**——主干（`retrieval/`）的优先级由此获得外部支撑 |
| **Entity Tracing Framework**（ACL 2025；人工标注 **411 条代码摘要 / 9,933 个实体**） | **31.63% 的摘要至少含一个幻觉实体**（实体级错误率 3.05%），检测器 F1 73% | "AI 解释代码会编"首次有了**测得的发生率**，而非感觉 |
| **DeepWiki 的公开翻车**（HN 231 分 / 53 评论，本类最高分帖） | LLVM：*"ranged from incomplete to just plain **incorrect**… The high-level compilation pipeline diagram is… **wrong**?"*；*"the diagrams are **not engineering quality**"*；LibreOffice 维护者：*"We didn't ask for **deceptive garbage** to be generated as documentation"*；有人被 DeepWiki 生成的错误 bug report **浪费了一小时** | 头部免费工具**正在公开地给出错误架构**。注意评论里那条最关键的技术判断：那是"**比例错误（把外围 build 文件当成主系统），不是编造**"——**这正是检索排序没命中正确节点**，与本文 D2 的失败模式**同类** |
| **SO 2025（n=31,476）** | **61.3%** 说即使 AI 做了大部分编码，他们仍会**找人**来"**彻底理解某件事**"；只有 4.3% 认为不再需要人 | 对"真理解"的需求**在 AI 时代存续**，而不是被替代 |
| **AI 验证痛点的量化** | "几乎对但不对" 66%；AI 缺代码库上下文 63.3%/64.6%；不信任输出 66.2%；引入 Copilot 后核心开发者**评审量 +6.5%、自身产出 −19%** | **"证明你读懂了 agent 写了什么，再合并"** 比"上手这个仓库"更紧迫、更团队级 |

**综合判断**：**本品类最大的可攻击面不是"图画得不够好"，而是"没人验证这些结论是否真的锚定在代码上"——而 Fieldguide 已经建好了测量仪器**（`src/main/eval/`：Recall@k / MRR / 引用精确率 / 忠实度 / 幻觉率）。这比"我们也有图谱"高一个量级。

**⭐ 两条最有杀伤力的原话（调研全项目最佳引用，直接指向出口 C 的设计）**：

> **① 从业者描述的病症**（HN "comprehension debt" 帖，532 分）：
> *"I've seen tools designed to 'understand' and document repos **hallucinate many times, often coming up with a plausible but completely wrong explanation of how things actually work**… while I could catch that because I wrote the code in question… **others do not have that benefit.**"*

> **② 品类领先者自己承认了这件事**（DeepWiki 作者，HN 43799251）——**这一句对每个"我们有 grounding"的说法都是致命的**：
> *"you can never exclude hallucinations entirely… **The reason we display the code snippets is to make it easy to double check with the source.**"*
> **翻译：厂商承认它对抗幻觉的办法，是把核对工作交给读者。** 它把验证负担**外化**给了用户。

**这两句一起，把"可信"从我方的一厢情愿，变成了竞品自己承认的结构性缺陷**——而 Fieldguide 的出口 C（锚定徽标 / 引用可验证 / 出处 / 新鲜度）正是**把这份负担收回产品里**。这是本文所有主张中最有外部支撑的一条。

> **因此本文的主干（`retrieval/` + 能力协商）不是重构洁癖，而是对齐本品类测得的瓶颈。** 这也解释了为什么 D2 必须排在第一位修。

### 1.8 ⭐ 两个新证据，改变优先级：**"锚定 + 稳定"无人做到，且知识流失比"上手慢"可引用**

这是最后一轮调研带来的、我认为**比学习闭环更值得下注**的一条：

| 新证据 | 内容 | 为什么它比学习闭环楔子更可辩护 |
|--------|------|------------------------------|
| **没有工具同时做到"锚定"与"稳定"** | **Google Code Wiki 最尖锐的抱怨是不确定性**：重新生成的内容*"the next day… is **completely different**"*。所以本品类每个工具二选一：**要么每次重新生成（不稳定、无法长期引用/签署），要么是静态的（会腐烂）**。**没有任何被调研的工具提供一个"既锚定代码、又稳定到可以评审或签字确认"的知识层** | 这是**确定性属性**（做得成/做不成可验证），**不需要用户研究就能判定可行性**；且**没有 0★ 先例的墓地**（与学习闭环相反，§3.9.4） |
| **"保管人确认"空白** | **没人记录"是谁在什么时候确认了这条结论"**（custodian-verified architecture） | Fieldguide 的 **Obsidian 托管块所有权模型**（`%% fieldguide:begin/end %%` + 块外字节级保留 + 冲突三选一）**已经就是这个机制**——它是"稳定的生成内容 + 人工内容不可覆盖"，只差把"谁确认/何时"露出来 |
| **知识流失已高度量化**（比 onboarding 数据强得多） | **65% 的 133 个热门项目 truck factor ≤ 2**（ICPC 2016, arXiv 1604.06766）；**89% 的 36,000+ 项目失去了核心团队、只有 27% 被替换**；新人只吸收了 **16%** 的孤儿文件，其余落到最忙的专家身上 | 知识流失是理解问题的**组织形态**，而且**数字可引用**：*"你的 bus factor 是 1–2，89% 的项目会失去核心团队"*——**这比"我们能加快上手"强得多**（后者正是 DORA 未能证实的那个主张，§3.9） |

**因此本文的优先级做一处调整**：

- **出口 C 的"新鲜度证明 + 出处（谁在何时确认）"从"三个补充空白"升格为与出口 A 并列的第一候选楔子**——理由：它与**竞品自认的缺陷**（引用②）直接对应，是**确定性**目标，且 **Fieldguide 已有 Obsidian 所有权模型这件现成零件**。
- **学习闭环（出口 A）保持为旗舰体验，但仍必须过 §五.6 的两周证伪门禁**（免费侧 0★ 先例 + 零需求证据）。

**⭐ 第三条降低学习闭环权重的理由：变现天花板已被测出——而它的疗效证据比我初稿写的弱。**

⚠️ **本文 v1.4 在此处犯过一个错误，现更正**：我写过"Anki 采用率 94%/82%，**USMLE 分数提升 4–13 分**"。**那个分数提升的数字已被调研者本人撤回**——可核实的三篇医学研究（PMID **41322734** / **41939075** / **41862940**，经 Europe PMC 核实）**全部是观察性、横断面研究**，其中一篇标题里就写着 *"a cross-sectional study"*；**它们只支持相关性，不支持因果。** 另有一个被提供的 PMID（**42183420**）**在 Europe PMC 里查不到，因此不予引用**。

> **可用表述只能是**：Anki 在医学教育中**采用率很高**（94%/82%），且 Anki 式学习与更好的考试成绩**相关**——**分数提升幅度属于"关联性"证据，需等一个实验性来源。**
>
> **元教训（调研者自己给出的，本文照录）**：**别人递给你的引用，无论看起来多具体，都是一个待核实的"主张"，不是可以直接搬运的"事实"。** 一个 PMID 看起来像是已核实——**把它解析出来才是核实。** 这条对本文同样适用：我上一版就是直接搬运了它。

**而变现天花板这一半独立成立**（不依赖上述疗效证据）：Anki 本体免费，**AnkiHub 的档位是 免费 / $6 / $10 每月 / $450 终身**——即**建立在免费内核之上的个位数美元**。

> **SRS 应当作为产品内部的留存机制，而不是它的定位或价格锚。** 一个把自己定位成"给代码用的间隔重复"的工具，会**继承这个天花板并同时面对一个免费竞品**。

**注意这处更正的方向**：疗效证据被削弱，**反而让"不要把 SRS 当定位"这个结论更稳**——若连最强的现实证据都只是相关性，就更没有理由拿它当旗舰卖点。这与 §1.8 的"确定性优先"结论同向，也是我把出口 A 从"楔子"降为"内部机制 + 待证伪体验"的第三个独立理由。

**诚实边界（必须随数字一起讲）**：

- 「58%」是一手同行评审研究，但**是 2018 年的、生成式 AI 之前的数据**；目前**没有**同等规模的后 2023 年复测。引用时必须带上年份。
- 「学习代码库 +9.7pt」**不是**最大的需求缺口（代码评审 +27.7pt、测试 +19.0pt 更大），且该环节的**明确不感兴趣比例最高（18.7%）**。可辩护的说法是「这是一个大且工具不足的环节，有相当比例的人明确想要帮助」，**不能**声称它是最大需求信号。
- Stack Overflow 样本是**自选择**的（其方法论自陈：主要通过 Stack Overflow 自有渠道招募，重度用户更易看到问卷）。
- JetBrains 的 DevEx 数据为**厂商自发发布**（其销售 IDE 与 AI 工具），仅作方向参考。
- **⚠️ HN 的计量口径**：**HN 只有主帖有点数，评论本身没有分数**。本文凡引用评论内容，其"分数"一律是**所属主帖的点数**（调研已声明为 proxy）——所以不能说"某条高赞评论"，只能说"某高分帖下的一条评论"。上文的 532 分指主帖。
- **⚠️ 已被调研证伪、不得引用的常见数字**：「开发者中位任期 ≈2 年」（BLS 实为 **4.3**）；「替换一名员工 = 6–9 个月薪资」（所引 Gallup 页面**已 404**）；COBOL 系列传说（"95% ATM 刷卡"、"每日 $3T"）。
- **⚠️ CodeSee 收购**只以实际抓取到的两家行业报道为准（SD Times、FinSMEs）；**GitKraken 自己的新闻稿返回 403、未抓取**，仅作为"主张出处"而非已核实来源。
- **⚠️ 开放需求证据的空白**：Reddit 全程 403，故定性基础偏 HN；**付费意愿未被测量——所有需求信号都是注意力，不是预算**；且**没有任何具名西方企业公开表示"因为政策禁止上云所以跑本地模型"**，因此"西方企业对离线的付费意愿"是**推断，不是已核实**。
- 上述外部调研的原始取证材料在 `docs/research/`（含一手页面与数据集），可复核；其中「81% 开发者评审时间增加」一项**来自厂商 Harness、样本量未公开，评级 Low，不建议引用**。

### 1.9 ⭐⭐ 当前最强的需求侧证据：**理解是写的 2 倍痛，且开发者不愿把它外包给 AI**

这一节是整份调研里**对本文定位最有力的证据**，且它比 2018 年的「58%」更好用——**它是当前的、直接对比的、并且是问题陈述而非有争议的时间分配估计**。两项都来自**重算 JetBrains 自己的原始受访者微观数据**（不是其文案）。

**⭐ 可复现性出处（本节数字若不给出处就是不可复核的——这也是调研刚给自己补上的一个洞，本文同样补上）**：

| 项 | 值 |
|---|---|
| 数据源（均已抓取，HTTP 200） | **State of Developer Ecosystem 2025 `RawData.zip`**（98 MB，**4,740 列 × 24,534 行**）与 **2024 `RawData.zip`**（87 MB，**6,208 列 × 23,262 行**） |
| 交叉验证 | **行数与 JetBrains 公布的样本量一致** |
| 加权方法 | **Goldfarb & Idnani (1982/1983)** 加权 |
| ⚠️ 未能核实 | **2023 年的微观数据返回 403**，无法检查 |

| 证据（JetBrains 微观数据重算） | 数字 | 含义 |
|-------------------------------|------|------|
| **"理解别人的代码"是主要挑战** vs **"写代码"** | **31.6% vs 15.6%（2025）**；**28.6% vs 13.8%（2024）** | **理解 ≈ 写的 2 倍痛，且该比值连续两年稳定。** 这是比"58% 的时间花在理解上"更干净的开场数字 |
| **最不愿交给 AI 的活动就是"理解代码"** | **42.9% 仍要自己做代码理解，只有 34.4% 愿意委派**（对比：调试 47.5% 愿委派、代码评审 38.2%） | ⭐ **开发者想把"理解"留在自己手里**——这是**直接的需求侧证据，支持"给人用的理解产品"，而不是"替人理解的 AI 产品"** |

**⚠️ 必须随行的偏差限定（否则本节最强证据反而最脆弱）**：

- **JetBrains 主动披露并修正了自身的受访者偏差**——把 JetBrains 用户占比**按 ×0.9 下调 10%** 以抵消过度代表。这**值得肯定（少见的坦诚）**，但它同时确认：**本文所倚重的数字里仍残留对 JetBrains 用户的偏向**（受访者更可能是 JetBrains 生态的开发者）。
- 因此本节的正确用法是**方向性**（"理解比写更痛、且人们不愿外包"），**不是精确的总体比例**。JetBrains 自己的方法论原文（已核实逐字）是：*"Despite these measures, some bias is likely present, as JetBrains users **might have been more willing, on average, to complete** the survey."*

> **一条方法论教训（调研全项目最有启发性的一处错误，本文照录）**：某条被当作**逐字引用**转述的 JetBrains 方法论句子，实际上是**语义相近但并非原文的改写**——*"Some bias may remain, as JetBrains users could have been more likely to respond."* 而**真实的现网措辞**是上面那句。**这种"貌似可信的近引"能通过所有随意复核，只有真正去抓页面才能发现它。** 而且它出现在一句**无关紧要**的话里——**低风险处恰恰是改写最容易溜过去的地方。**

**为什么这两条对本文至关重要**：v1.3 我把定位押在「**证明人读懂了**」而非「证明代码没坏」（§1.6.2 / §1.8）。当时它的支撑是 Lacy 的测验分数（单公司、未复现）。**现在有了需求侧独立支撑：理解是最大的痛，而且人们明确不愿意把它外包。** 这让「人的理解」从一个"我们选了它"的主张，变成"**用户自己指向的方向**"。

**第三条：人类评审才是约束，不是代码产量**（NBER WP 35275，**500,000+ GitHub 开发者，本调研最大样本**）：

> AI 使 **提交数 +240%，而发布数仅 +30%**；核心开发者**评审量 +6.5%**，同时其自身产出**−19%**。
> → **人类评审是瓶颈，不是代码生产。** 这与另一份较小样本的独立复现一致（arXiv 2510.10165），也把本品类的痛点从"写得太慢"改写成"**验得太慢、读不过来**"。

**与 DORA 的诚实配对**（两句话必须一起说）：

- **DORA 2023（正向，且是本次调研最强的正向商业数字）**：*"new hires on teams with well-written documentation (1 standard deviation above average) are **130% as productive** as new hires on teams with poorly written documentation (1 standard deviation below average)"*（PDF p.55–56，n≈3,000）。旁证：**高质量文档 → 25% 更高的团队绩效**、*"1.4x more impact on organizational performance"*（样本 36,000+）。
- **DORA 对"文档质量作为新人 ramp 杠杆"的检验为 null**——**注意这与上一条出自同一段，不是矛盾**：DORA 原话是这些做法 *"do help new hires, but… **new hires don't get any special benefits from these practices**"*。
- → **合起来的意思是：知识质量是一个很大的"普遍"生产力杠杆（130%），但没有"新人专属"的加速效应。** 所以对外应挂**"知识质量 / 团队生产力"**与**评审信心**，**不挂"更快上手"**。
- ⚠️ **130% 必须随行两条 DORA 自己声明的限定**，否则一次像样的质询就能推翻它：① **横断面的 ±1 标准差比较，不是实验**（*"our data is not experimental… it is difficult to draw sharp conclusions"*）；② **不是新人特异的**。
- ⚠️ 顺带订正一条常被误引的统计：**DORA「2024」的结论是双负**（每 +25% AI 采用率：吞吐 **−1.5%**、稳定性 **−7.2%**，标题即 "AI is hurting delivery performance"）；**"吞吐转正但稳定性仍受损"是 2025 年报告**。本文未使用该数字，但列在此以防后续引用出错。

**⚠️ 关于「58%」的溯源精度（必须收紧措辞）**：

- 可信的测量是 **Xia et al., IEEE TSE 44(10):951–976, 2018**（7 个项目 / 78 名职业开发者 / 3,148 工时）。
- 它的**祖先引用 Fjeldstad 1983 确实存在于该文参考文献中**（经 Crossref 确认），**但那项测量本身无法获取**——**引用可核实，数字不可核实**。因此只能说"作者所引的一个祖先来源"，不能说"可追溯的一手来源"。
- 另有两处常见误引：**Thomas Ball 不是该文作者**；该数字常被标为 1990 年代，而**可信测量是 2018 年**。
- **并且在本文中，建议用 §1.9 的 JetBrains 2 倍对比替代 58% 作为开场数字**——它更新、是直接对比、且不依赖有争议的时间分配估计。

### 1.10 ⚠️⚠️ 先例检验：**Fieldguide 的分发策略已被 Sourcegraph 试过并公开关停**

这是整份调研里**最强的一条反证**，因为它检验的是**策略**而不是功能——而它检验的正是本文 §2.3 / §3.9 所依赖的那套打法。

**Sourcegraph（一家有资金的公司）做过与 Fieldguide 形状一致的事**：一个**免费的本地桌面代码理解应用**，明确定位成付费云产品的漏斗。**出处是 Sourcegraph 自己的公开手册**：

> *"it gets **individual devs** up and running with a Cody-supported Sourcegraph instance quickly, easily, and **for free**"* → *"They use **Sourcegraph App** locally on their code → They **upgrade to a Cloud trial**"*

**它的公开成功指标只有：下载量、试用启动数、CTA 活跃度——没有 CI、没有 PR 面。** 这与 Fieldguide 的产品形状、漏斗逻辑、以及**测量方式的薄弱**完全一致。

**结果**：**发布帖在 HN 只拿到 1 分**；**Cody Free/Pro 于 2025-07-23 被删除**；更早的整条弧线是三段式崩塌（OSS 未公告转闭源 444 分、仓库转私有 424 分、免费层被砍）。

> **含义（必须直说）**：Fieldguide 提出的**不是一个新颖的进入市场方式**——它提出的是一个**资源更好的竞争者试过、用同样不充分的指标衡量过、然后关停的打法**。**任何此类计划现在都需要一个比"下载量"更好的指标。**

**同时也要看到另一半——the shape *can* work，但机制完全不同：**

| 正面先例 | 数字 | **机制（这才是教训）** |
|----------|------|----------------------|
| **Bruno**（本地优先、Git 原生的桌面工具） | **约 250k MAU（2025-01）→ 600k+（2025-12）**，峰值单月新增 25 万用户，star 26k→40k，**HN 发布 1,538 分**（已审计） | **Bruno 赢在"移除一项强加"，而不是"功能更多"**——它打的是 Postman **强制账号**（365 分帖）。它是靠"**别逼我注册**"赢的，不是靠超越谁的功能 |
| **Atom**（GitHub 把它推向云端后关停） | HN **1,320 分** 帖 | 用户对"被推向云端"的反感是**已量化的** |

**⭐ 这条直接给出了 Fieldguide 唯一有证据的打法，并让 出口 C 的地位再升一级**：本品类**已被记录的"强加"清单**是现成的——

1. **无法核验的 AI 解释**（而厂商自己说"显示代码片段是为了让你自己去核对"，§1.7 引用②）；
2. **默认上传代码库**（智谱 ZCode，默认开启且无关闭开关，§2.4）；
3. **默认开启遥测**（codegraph 被点名）；
4. **只有云端的 repo wiki**、**强制账号**。

> **出口 C（锚定徽标 / 可验证引用 / 出处 / 新鲜度）+ 出网边界，本质上不是"差异化功能"，而是"移除第 1 与第 2 项强加"。** 这正是 Bruno 的机制在 Fieldguide 语境下的对应物——**比"我们也有知识图谱"有据得多，也比"我们的 AI 更聪明"可辩护得多。**

**⭐ 一条具体的、便宜的、且阻断全部价值的产品动作**：**给 Windows 安装包做代码签名与公证**。HN 上关于安装摩擦的原话是 *"code signing… notarizing (\$99 a year)… just not worth it"*（398 分帖），而**未签名的 Electron 应用会在用户看到任何价值之前先撞上 SmartScreen**。本仓当前 `package.json` 的 `win.signAndEditExecutable: false` 且无签名配置，`gap-analysis §2.4` 也记着"无代码签名"。**这笔 \$99/年 是本方案里投入产出比最高的单项之一**（已加入 §3.1 的 P0）。

**关于"上架市场"的纪律**：已审计的渠道规模——VS Code Marketplace 的 `ms-python.python` **237.8M 安装**、Copilot **74.6M**、微软一方称 **50M 月活开发者 / 100,000+ 扩展**；MCP SDK **40.3M npm 周下载**，`modelcontextprotocol/servers` **90,546★**。

> ⚠️ **计量口径警示（本调研抓到的一处真实陷阱）**：**这些是累计安装量，不是活跃用户数**；而且本品类里在流传的 AI 工具用户数**彼此不可比**——例如 Copilot 的">15 million（2025-04，时点值）"与"more than 20 million（2025-07，**历史累计用户**）"若被读成"一个季度增长 33%"，**是错的**。同理，**扩展安装数 ≠ 用户数**。
> 这一条恰好**加强**了本节的论点：**渠道数字看起来极大，恰恰因为它们是累计口径、且处在 10 万+ 扩展的竞争场里——所以"上架某个市场"不是策略。**
> **渠道极大，恰恰说明"上架某个市场"不是策略**——那里已有 10 万+ 扩展在争夺同一批安装。**MCP 因此只是互操作入场线**（缺失即取消资格，见 §3.1 P1），**绝非分发策略**：它是让别人能连上我们，不是让别人找到我们。

**⚠️ 对 PM 的当头一句**：本文建议的"开源 + 一个可证明的数字"如果把成功定义成**下载量 / star 数 / 试用数**，那它就是在重走 Sourcegraph App 的路。**可辩护的成功指标只有两类**：① 理解类（体检分数的区分度、用户是否回来做第二次，§3.7 的 A9/A10）；② 检索类（Recall@k / 幻觉率，对标本品类测得的瓶颈）。**这也是我拒绝用"用户数"作为本方案验收项的原因。**

### 1.11 Swimm 的第二次转向给出的重新定位选项：**一张图，两个买家**

> **⚠️ 证据分级声明（必须保留，这是调研者自己加的标注）**：本节的**证据**只有两条——**Swimm 现行官网的原文**（一手抓取，HTTP 200）与 **Stack Overflow 2024 的既有数字**。**"agent 上下文是更好的楔子"这一判断是推断，不是发现。** 请 PM 把它当**待权衡的选项**，而不是继承一个结论。

**Swimm 的第二跳值得单独看**：它没有停在"服务主导的主机现代化"，而是**把知识库卖给了 AI 而不是卖给人**——*"Build the validated knowledge base **your AI tools need to understand your codebase**. Copilot, Cursor, Claude Code, internal agents, MCP servers."*

**这暗示一个 Fieldguide 可以一图两卖的形态**：

| 买家 | 卖什么 | 预算行 | 本方案里对应的资产 |
|------|--------|--------|-------------------|
| **工程负责人（人）** | 人的理解证据：体检分数 + 出处 + 新鲜度（**可签字**） | 工具预算（§3.9：工具预算不足 24% > 培训不足 14%） | 出口 A + 出口 C（`comprehension.md` / `attestation.md`） |
| **AI 工具（agent）** | **被验证过的图谱上下文**：设计理由 + 出处 + 新鲜度，经 MCP 供给 Copilot / Cursor / Claude Code | **AI 工具预算**（在增长，且不与人抢一条没有验证买家的"学习"预算） | 出口 B 的 `AGENTS.md` + P1 的 MCP server |

**两个方向的需求侧信号（真数字，都来自本调研）**：

- **支持 agent 侧**：**64.6%** 的专业开发者说 AI 工具 *"lack context of my codebase"*（SO 2024，n=24,496）——**这是本调研最大的单个数字**。
- **支持人侧**：**42.9% 仍要自己做代码理解，只有 34.4% 愿委派**（§1.9）——人们**不愿把理解外包**。

**而 AI 辅助"学习代码库"的采用率只有 30.9% / 意愿 40.6%**（SO 2024）——**明显小于 64.6% 那个数**。

> **诚实解读，两面都说**：
> - **对本文的人侧定位不利的一点**：64.6% 这个最大的数字**指向的是"让 AI 别搞错"，不是"让我学会"**。若只看数字大小，agent 侧的需求信号**更强**。
> - **但对人侧仍有独立支撑**：42.9% 不愿委派是**动机证据**，且它解释了为什么"AI 替你理解"这条路上已经挤满了免费产品，而人侧空着。
> - **两者不矛盾**：它们是同一个痛的两个出口，**而且共用同一份资产**（一张被验证、稳定、可追溯的图）。这正是"一图两卖"在技术上是自然的原因。
>
> **⚠️ 但不要把这当成免费的午餐**：**agent 上下文正是 graphify 的主场**（116k★ / YC / agent-skill 形态 / 已 ship MCP，§1.6.1），DeepWiki、Code Wiki、Zread 也都在这里。**在 agent 侧 Fieldguide 是三重后进者；在人侧它至少还空着。**

**⭐ 因此对 MCP 的判断要收紧一格（修正 §四 与本方案原表述）**：

> **有一个 MCP server = 卫生（每个像样的厂商都有，缺失即取消资格）；把图谱"知道而 agent 会搞错的东西"当产品卖 = 生意。**
> **Fieldguide 无法在传输层差异化，只能在内容层**——也就是**设计理由（why）+ 出处 + 新鲜度**（回到 §1.8 与调研的"四个内容空白"）。**这恰好又是同一份资产。**

**对本方案结构的影响**：三个出口不是并列的三个功能，而是**一份资产的三条交付路径**——出口 C 是"给人与合规"的证明形态，出口 B 的 `AGENTS.md`/MCP 是"给 agent"的上下文形态，出口 A 是"给人"的测量形态。**这也让 §1.8 那个"确定性"楔子比我在 v1.3 评估的更有价值：它同时对着两条预算行，而不是一条。**

## 二、解决方案：一个引擎 + 三个出口

### 2.0 总图

```
                    ┌──────────────────────────────────────────┐
                    │  主干 · Understand Engine（检索与证据层） │
                    │  归一化 → 三通道检索 → 融合 → 证据包      │
                    └──────────────────────────────────────────┘
                          ↑              ↑                ↑
         ┌────────────────┘              │                └──────────────┐
         │                               │                               │
  ┌──────┴───────┐              ┌────────┴────────┐            ┌─────────┴────────┐
  │ 出口 A       │              │ 出口 C          │            │ 出口 B           │
  │ 读懂度体检   │              │ 可信度外化      │            │ 导览包（静态站点）│
  │ 留存 · 旗舰  │              │ 差异化 · 信任   │            │ 增长 · 传播      │
  │ 测 / 评 / 进 │              │ 引用可验证      │            │ 交付 / 交接      │
  └─────────────┘              └─────────────────┘            └──────────────────┘
```

- **主干解决 D2**（让旗舰能力成真）：一处升级，Agent / 搜索框 / 评测三处同时受益。
- **出口 A 解决 D1**（补上「评」与「进」，形成复利）。
- **出口 B 解决 D3**（产物可传播）。
- **出口 C 解决 D4**（能力外化为可见数字）。

### 2.1 主干 · Understand Engine（检索与证据层）

**动因（架构层面的硬理由）**：当前「检索」散落在四处、各自实现、各自演进——

| 位置 | 现状 |
|------|------|
| `src/main/ua/search.ts` | 面板搜索走这里（Fuse.js） |
| `src/main/agent/tools.ts` | Agent 的 `search_nodes` 走这里 |
| `src/main/agent/context-packer.ts` | 回答前注入上下文（10k 字符预算） |
| `src/main/eval/harness.ts` | 评测走这里 |

**后果：评测里测的检索 ≠ 产品里跑的检索。** 评测文档能写出「语义检索 68%」，而用户实际体验的是另一条路径——这是 D2 能够长期隐身不被告警的根本原因。收敛为一层后，**评测与产品同源**，指标才有产品意义。

**新增 `src/main/retrieval/`（六个模块，职责单一）：**

| 模块 | 职责 | 关键设计 |
|------|------|----------|
| `capability.ts` | **能力协商**：启动/配置变更时探测并登记「本配置真实可用的能力」（chat / embedding / 多语言 embedding / 向量索引是否已建） | **D5 的根治**。原料已存在：`llm/catalog.ts:121-125` 已按 `looksLikeEmbeddingModel` 分类并给出 `embedModels`，只需把结果**固化为运行时能力位**，并在设置页与状态栏显式展示。任何依赖 embedding 的功能在能力位为假时**不静默编造模型名**（修掉 `vector/embed.ts:30,77`），而是给出可操作指引 |
| `normalize.ts` | 查询归一化：CJK 分词 / 停用词 / 英文标识符抽取 / 中→英术语改写 | 词典优先、LLM 兜底；带 LRU 缓存；**离线可用**（词典路径不依赖 Key）。**这是不依赖 embedding 的主力通道** |
| `lexical.ts` | 词法通道（保留现有 Fuse）+ **符号精确通道**（标识符 / 文件路径 / 全大写常量） | 符号通道对「`handleRequest` 在哪」这类问题几乎零成本高收益 |
| `vector.ts` | 向量通道：节点文本嵌入 + 余弦检索 | 复用 `src/main/vector/embed.ts:23,69,114`；上游 `SemanticSearchEngine` 可直接用。**可选增强**：仅对声明了 `embedModels` 的供应商生效（openai / moonshot / siliconflow / openrouter / ollama 5 家；**DeepSeek 无 embedding 端点，实测 404**） |
| `fusion.ts` | RRF 融合 + 去重 + 按类型/分层加权 | 融合优于单通道是检索领域共识；权重可被评测集调优 |
| `evidence.ts` | 统一证据包：节点 + 行号 + 邻居 + 分层 + Tour 位置 + 论文片段 | 供**回答生成**与**出口 C 可信度校验**共用同一份证据 |

> **降级链（务必显式，且对用户可见）**：
> `向量 ⊕ 符号 ⊕ 词法` → （无 embedding 能力时）`归一化后的符号 ⊕ 词法` → （无 Key 时）`纯词法`
> 每一档都在 UI 上写明当前后端——复用 `searchNodesDetailed()` 已有的 `backend` 字段范式（`src/main/ua/search.ts:31-37`）。**永远不再出现「静默降级成假语义」。**

**与既有硬约束的相容性（逐条核对，全部满足）：**

| 约束 | 出处 | 本方案 |
|------|------|--------|
| 禁止自研 Tree-sitter parser / `GraphBuilder` / Dashboard 布局、LOD、Tour 播放器 | `understand-anything-integration.md:221-225` | 完全不碰；只用上游**已导出**的 `SemanticSearchEngine`（`core/src/index.ts:17`）——**零 fork、零上游补丁** |
| 图谱 nodes/edges **不写入 SQLite** | `doc-index.md:17,218` | 向量索引是**派生缓存**，落 `.understand-anything/embeddings.f32` sidecar + `embeddings.meta.json`（按 mtime + contentHash 失效），**不进 `app.db`、不进 `knowledge-graph.json` 主结构** |
| 本地优先 / 源码与图谱不出本机 | `product-spec.md:199` | 只把节点文本送给用户自己配置的 embedding 端点，与现有论文 RAG / LLM 富化行为一致 |
| 读路径不得写用户项目文件 | `gap-analysis §2.1 #3`（已修） | sidecar 只在**索引/维护路径**写；读路径只读 |

**顺手修掉的一个真实性能缺陷**：`src/main/ua/search.ts:184-188` 每次查询都 `new Ctor(nodes)`，即在 3656 节点（HIS-Go 规模）上**重建一次 Fuse 索引**。主干层改为按图谱身份（mtime + size）缓存索引单例——`graph-reader.ts:86,116-127` 已有同款缓存范式可照抄。

### 2.2 出口 A ·「读懂度体检」Comprehension Check（留存 · 旗舰）

**这是唯一能回答「我读懂了多少」的功能，也是把 Phase 6 的学习闭环接上「评」与「进」的那一环。**

**关键可行性洞察：出题不需要人工标注。**

现有评测集（`eval/datasets/pulsegate.qa.json`）的 schema 本身就是一个**带 ground truth 的题库**：

```json
{ "id": "q01", "kind": "locate",
  "question": "事件从 HTTP 入口进来之后，经过哪些环节才落到存储？",
  "expect": { "nodes": [...], "files": [...] }, "expectedHops": ... }
```

（`eval/datasets/pulsegate.qa.json:12-34`；`kind ∈ locate|explain|path`，见 `:6-11`）

**同一份 ground truth 既能给机器打分（`src/main/eval/metrics.ts` 已实现），也能给人打分。** 于是标注成本≈0，且题目天然可自动扩展：

| 题型 | 生成方式 | 是否需要 LLM | ground truth |
|------|----------|:---:|--------------|
| **locate**「这个职责在哪个文件实现？」 | 取节点（按分层/中心度加权）→ 用节点摘要改写为问题 | 可不用（模板化） | `node.filePath`（图谱自带） |
| **path**「把这条调用链排成正确顺序」 | 复用已有的 `findPath()`（`src/main/ua/graph-reader.ts:205`，BFS 已实现） | **不需要** | 图谱里的真实路径 |
| **explain**「为什么这里用 X 而不是 Y？」 | 由节点摘要 + 语言要点生成 | 需要 | 节点本身 |
| **application**（**最重要，新增**）「要新增功能 F，需要改哪些文件？」 | 从需求描述取种子节点 → 沿 call/import 闭包推出应改文件集 | 需要（生成需求描述） | **变更闭包（图谱可算）** |

**为什么必须有 application 型题（有实验依据，不是口味）**：间隔重复的证据对**回忆（recall）**强、对**迁移（transfer）**弱——多选/定义型测验**没有**改善新情境下的应用表现。而 application 型题（"要加 F 要改哪些文件"）测的正是迁移，也**最接近真实工作**。因此：**做应用题，不做闪卡。**

**三类（locate / path / application 的路径部分）可离线生成**——这意味着**未配 API Key 的用户也能做体检**，直接命中 `doc-index.md:183` 的验收条款「无网络 / 无 API Key 时静态浏览流畅」。

**⭐ 独立学术证据：这个楔子是对的，而且它是本产品唯一能变成"数字"的东西**

> **Lacy — "Simulating Expert Mentoring for Software Onboarding with Code Tours"，FSE 2026 Industry Papers（arXiv 2603.25391），已部署于 Beko 生产环境**，在一套 **30K+ LOC 遗留金融系统**上做对照研究：
> **"Learners using expert-guided tours achieved 83% quiz scores versus 57% for AI-only tours"**，学习者更偏好 Tour 而非自学，且认为需要的专家咨询更少；**Beko 随后采纳 Lacy 做组织级 onboarding**。Lacy 的组成里就含 **comprehension quizzes + dashboard**。

三点结论，每一点都改变本文的设计：

1. **26 个百分点的差距，是"专家策展"与"纯 AI 解释"之间的距离。** 而**纯 AI 解释正是已被商品化的那一侧**（DeepWiki、Code Wiki、graphify、Doculearn）。→ **Fieldguide 现在的卖点"LLM 由图谱锚定"只是一个"机器锚定"故事；Lacy 表明更强的故事是"锚定在团队自己的 why 上"。**
2. **测验分数是本产品唯一的"可证明数字"。** 竞品能把"71.5× fewer tokens"写进徽章，Fieldguide 卖的是"理解"——**只有体检分数能把它变成一张能放在幻灯片上的表**。这是出口 A 从"留存功能"升格为"**营销口径**"的理由。
3. **它同时验证了"学习闭环"这个楔子**：商业竞品（§1.6 全部）没有一个做测验或留存机制。

**⚠️ 必须同时讲的风险（否则就是选择性引用）**：调研的差距/痛点证据档案（**126 KB / 约 146 条原文引用 / 235 条来源链接**）**没有找到"进度 / 间隔重复 / 面试题"的需求证据**——这个楔子是**差异化但未经需求验证**的。Lacy 本身也是**单公司、单系统、quiz 分数只是理解的代理指标、未被独立复现**。因此 W3.5 门禁必须包含**一次真实用户的体检可用性测试**（N=3–5），否则我们是在用一个有实验支撑但无需求证据的功能做旗舰。

**关于"策展 vs 生成"的架构含义（重要）**：如果 26 分差距的来源是**专家 why**，那么本方案不能只做"自动出题机"，必须让**人能策展**：用户/团队专家能编辑 Tour 步骤、给节点补"为什么这样设计"的理由（`code_notes` 已有行级批注、Tour 已有结构），**体检则针对这份策展内容出题**。这把产品从"AI 生成解释"移到"**策展 + 测量**"——后者是竞品没做的，也是 Lacy 证明有效的那一侧。**这是本提案相对原方案最重要的一处设计修正。**

**流程与产出：**

```
选范围（整项目 / 某分层 / 某模块）
   → 自动出题（locate + path 离线可出，explain 需 Key）
   → 作答（点文件 / 排顺序 / 选择）
   → 打分：总读懂度分数
   → 盲区热力图：错题映射回 分层 / 模块（复用图谱分层着色）
   → 自动生成学习路径：错题节点排序成一条 Tour，写回 graph.tour
   → 产出「读懂度报告」：可导出（复用 insights.ts 报告生成 + Obsidian 卡片）
```

**复用清单（几乎不需要新基础设施）**：`metrics.ts` 打分、`findPath()` 出路径题、`ProgressPanel` 承载 UI、`cross-tour.ts` 的归一化合并写 Tour（**注意**：必须用合并语义，勿覆盖既有 Tour——`gap-analysis §2.1 #4` 踩过这个坑）、`insights.ts` 出报告。

**数据模型**：新增 `comprehension_runs(project_id, scope, started_at, finished_at, score, detail_json)` 一张表 + 2 个 IPC，按 `db/migrations.ts` 的 `user_version` 范式迁移（`gap-analysis §2.4` 已铺好）。

### 2.3 出口 B ·「导览包」Project Bundle（增长 · 传播）

**一键导出一个自包含、可托管的目录（相对路径自洽，可挂任意静态托管）：**

```
<项目名>-fieldguide/
  index.html            # UA Dashboard 构建产物（只读模式）
  config.json           # locale / 只读标志
  data/knowledge-graph.json
  tour/*.md             # 架构叙事 / 分层说明 / 关键调用链
  AGENTS.md             # ★ 机器可读上下文：可直接喂给 Claude Code / Cursor
  comprehension.md      # 读懂度报告（出口 A）
  attestation.md        # ★ 理解证明 + 新鲜度声明（出口 C）
  serve.cmd             # 本地预览：一行启动静态服务（规避 file:// 的 fetch 限制）
```

`AGENTS.md` 与 `attestation.md` 是本设计相对朴素"导出网站"的关键增量：前者让产物**成为别人工具的输入**（借分发），后者让产物**携带可核验的信任信息**（见出口 C）。

**传播机制（按外部证据修正过）**：接收方打开无需安装 → 想自己给别人的仓库生成一份，就需要装 Fieldguide。**每个导出都是一次分发**。

但**原设计（本地文件夹 + `serve.cmd`）的病毒面几乎为零**——调研的结论很直白：**a purely local graph has zero viral surface**。本品类唯一真正突破的机制是**URL 可寻址**（DeepWiki 靠 `github.com` → `deepwiki.com` 换域名即看，231 分）。

**因此做两处修正**：

1. **导出物必须是"可部署的静态站点"**（相对路径自洽），能一行命令挂到 GitHub Pages / 任意静态托管 / 内网，从而**变成一个链接**。这仍然不违反非目标：**没有 Fieldguide 服务器、没有账号、没有 SaaS**——托管是用户自己的选择。
2. **必须同时导出"喂给 agent 的结构化上下文"**。HN 上对 DeepWiki 的最高评价不是图，而是两件事：**可追问的 follow-up**，以及**可带走的产物**——*"you can ask DeepWiki to provide a Markdown cheat sheet… drop that summary directly into Claude Code or Cursor as structured context"*。所以导览包里应含一份机器可读的 `AGENTS.md` 式上下文（架构 + 分层 + 关键调用链 + 概念桥接），**让 Fieldguide 的产物成为别的工具的输入**——这是 Fieldguide 唯一能借到别人分发的路径。

**场景价值（措辞已按证据收紧）**：写进仓库 `docs/`、交接材料、面试作品集、技术博客配图；**以及"理解证据"随 PR 提交**（见出口 C）。

**⚠️ 不要卖"更快上手"（这是本品类最弱的一个主张，且已被证否）**：

- **DORA 直接测过"文档质量作为新人 ramp 杠杆"，结果是 null**——**而且这与下一条是同一段结论，不是矛盾**。DORA 原话：*"these practices **do help new hires, but these practices do not help new hires more or less than everyone else**… **new hires don't get any special benefits from these practices**"*（对文档、AI、面对面协作都成立）。DORA 也不发布任何 "time to first contribution" 指标。
- 业界普遍引用的"**3–6 个月上手**"经溯源是**无出处的厂商传说（phantom citations）**；实测数字是 **6–7 个月**（中小项目）/ **最多 12 个月**（大项目）——Zhou & Mockus, FSE 2010。
- ⭐ **可辩护的挂靠方式（依调研的收口建议，改用最强的那个数字）**：**DORA 2023 的 130% 效应**——*"new hires on teams with well-written documentation (1 standard deviation above average) are **130% as productive** as new hires on teams with poorly written documentation (1 standard deviation below average)"*（DORA 2023 PDF p.55–56，n≈3,000）。
  → **对外主张应是"知识质量是整个团队的 130% 生产力杠杆"，而不是"我们加快上手"。** 这也终于给 Fieldguide 一个**可辩护的成果指标**：**文档 / 知识质量**——它恰好就是本产品真正改善的东西。
  ⚠️ **这两个限定必须随 130% 一起讲，否则经不起一次像样的质询**（均为 DORA 自己声明）：① 它是**横断面的 ±1 标准差比较，不是实验**（*"our data is not experimental… it is difficult to draw sharp conclusions"*）；② **它不是新人特异的**（见上一条）。
  （DORA 2023 另有 **"高质量文档 → 25% 更高的团队绩效"** 与 *"1.4x more impact on organizational performance"*，样本 36,000+ 专业人士——可作旁证，但 130% 是主打数字。）
- 另一条挂靠路径：**评审信心**（出口 C），因为它完全绕开 DORA 的 null 结果。调研给 PM 的原话是：**"prove you understand what the agent wrote, before you merge it" 比 "onboard onto this repo" 更锋利、更紧迫、更团队级。**

**与「非目标」的相容性核对**（重要）：这**不是** Web SaaS、不需要服务器、不需要账号、不是 IDE 插件——纯静态文件 + 用户自行托管，`product-spec.md:206-214` 的非目标全部不触碰。

**主要技术风险（已核实，诚实标注）**：Dashboard 经**特权协议** `ua-dashboard://` + 固定 embed token + postMessage 双向桥（16 下行 / 3 上行，`src/main/ua/dashboard.ts:142`）加载，且它是为绕过 UA TokenGate 而设计的（`:15`）。静态导出必须解决两件事：

1. **协议依赖**：`dashboard.ts:20` 的注释明确说明——普通加载方式会**拒绝 ES module 脚本与 fetch**，iframe 直接白屏。因此导出包**不能用 `file://` 双击打开**，必须配一个本地静态服务（导出 `serve.cmd`，一行命令）。这不是妥协，是既成约束。
2. **运行期端点**：UA CodeViewer 会 `fetch('/file-content.json?token=&path=')`（`:434`），该端点由 Electron handler 动态提供。静态包需**预物化**该 JSON——只针对 Tour / 架构叙事 / 热点引用的节点（受控体积），其余文件在只读模式下不提供查看。

**若上述任一项在 W0 Spike 中不成立 → 降级方案**：导览包退为「结构化 Markdown + 图谱 JSON + 一键本地静态服务打开」，并在 README 明确降级说明（**不自研画布**，遵守 `doc-index.md:106` 硬约束）。

### 2.4 出口 C · 可信度外化（差异化 · 信任 · **市场痛点第一顺位**）

> **优先级说明（依据 §1.4）**：独立调研显示开发者对 AI 工具排名第一的抱怨是**「缺少我所在代码库的上下文」（64.6%）**与**「不信任其输出」（66.1%）**。Fieldguide 恰好拥有回答这两个问题的技术资产（图谱锚定 + 引用溯源 + 忠实度指标），却**没有把它显示给用户**。因此出口 C 不是附属品，而是**投入产出最高的一项**（4 人日，且可独立上线）。

把已有但不可见的能力变成用户看得见的数字：

| 界面元素 | 数据来源（已存在） |
|----------|-------------------|
| 每条回答的「锚定徽标」：锚定节点数 / 引用校验通过率 | `evidence.ts` 证据包 + `metrics.ts` 引用精确率 / 忠实度（`:1-15`） |
| 「验证这条回答」按钮：把每条引用的断言跳回图谱与行号，未锚定的标红 | `evidence.ts` + 现有 `nodeRefs` 跳转链路 |
| 检索后端与降级提示（`ua-semantic` / `hybrid` / `lexical`）+ 命中分数 | 已有先例：`searchNodesDetailed()` 已返回 `backend` 字段（`src/main/ua/search.ts:31-37`）——**把这个诚实性机制扩展到全链路** |

价值：把「我们和 ChatGPT 有什么不同」从一句宣传变成用户看得见的一行数字；同时**让降级对用户透明**（没有向量能力时明确告知，而不是静默退化成假语义）。

**⭐ 并且按外部证据，出口 C 应当承担三件竞品都没做的事（调研的"四个真实内容空白"里有三个在此）——依 §1.8，这三件已从"补充空白"升格为与出口 A 并列的第一候选楔子：**

> **它比其他候选更可辩护的三个理由**：① **确定性**——"这条结论是否仍锚定在代码上 / 是否稳定到可评审"是可验证属性，不需要用户研究就能判定成败；② **直接对应竞品自认的缺陷**——DeepWiki 作者亲口说"我们显示代码片段是为了让用户自己去核对"（§1.7 引用②），**出口 C 是把这份被外化的验证负担收回产品**；③ **零件已存在**——Obsidian 托管块的所有权模型、`isGraphStale`、`metrics.ts` 都是现成的，而学习闭环在免费侧已有 0★ 先例（§3.9.4）。

| 空白（调研确认无人做） | Fieldguide 已有的零件 | 要做成什么 |
|----------------------|---------------------|-----------|
| **新鲜度证明**——"这条知识断言在某个 commit 之后还成立吗？"**没有人验证过** | `graph-reader.isGraphStale`（`:318`）+ `ua/diff.ts` 变更影响 + 图谱指纹 | **每条结论标注"验证于 commit X"**；图谱变脏时把**受影响的具体断言**列出来（"这 3 条可能已失效"），而不是只给一个 stale 徽标 |
| **出处（provenance）**——没人能区分"生成的内容"与"人写的内容"，维护者对此**正在生气**（OCaml/Julia 曾被 LLM 内容农场 SEO 压制） | Obsidian 侧已建好：`%% fieldguide:begin/end %%` 托管块 + **块外字节级保留** + 冲突三选一（`obsidian/render.ts`） | **把同一套所有权模型显示在应用内**：每个产物标注来源（模型 / commit / 时间 / 人工编辑过），人工内容永不被覆盖（规则已有，只是没露出） |
| **设计理由（why）**——没有工具重建"为什么这样设计、否决过什么"；而这是最贵的空白（Doculearn 的最高赞批评就是"缺 secret sauce 的 why"） | 知识卡的「原理 / 取舍」字段、`code_notes`、可编辑 Tour 的结构 | 让人（团队专家）能补 why，并**让体检针对这份策展出题**（§2.2 的 Lacy 修正） |

**为什么这比"可信度徽标"更值钱**：调研指出本品类头部工具（DeepWiki 等）**正在公开地给出错误架构**，且**没有任何产品能证明自己的结论还成立**。做一个"**能证明其结论仍锚定在代码上**"的工具，是一个**没人在守**的位置——而 Fieldguide 恰好在三处空白上都已有零件，只差把它们露出来。

**⭐ 还有一条：把"本地优先"从宣传语变成可审计的声明（ZCode 教训）**
> **ZCode 事故（2026-09-18）**：智谱的编码工具 ZCode —— 一个**整个品牌就是数据主权**的产品 —— 上线的**代码库索引 + Repo Wiki**（**正是 Fieldguide 的核心闭环**）**默认开启上传仓库数据，且客户端设置里找不到关闭开关**，加密公钥由服务端下发。恢复信任的代价是：当日道歉 + 热修 + **被迫开源客户端** + 中国信通院与绿盟两家第三方审计 + 移除该功能入口（v3.14.0）。
> 调研的结论原话：**"Local-first" is not a feature to list; it is a trust claim that must be auditable, default-off for egress, and provable.**

**这直接命中 Fieldguide 的一个真实缺陷**（`gap-analysis §2.4` 已记录，但被当作工程债而非信任债）：

| 现状 | 风险 |
|------|------|
| **渲染层直连外网**（`TheoryView.tsx:84` 直接 `fetch export.arxiv.org`，绕过主进程） | 出网不收敛——正是 ZCode 那类事故的**结构前提** |
| **无 CSP、无 sender 校验** | 渲染层被注入即可外发 |
| README 大量宣称「本地优先 / 源码不出本机」 | **是声明，不是证明** |

**建议把这三项修掉，并做成可见的"出网边界"**：出网走主进程白名单 + 可查看的出网日志 + 默认全离线可用。**成本已计入出口 C 的 4 人日**（本来就要改这两处）。

> ⚠️ **但必须撤回本文初稿的一句判断**：初稿说"可审计的零外发是一个空位"。**它不是空位。** Graphify Labs（YC S26）正用几乎逐字的措辞营销这一点——*"runs entirely inside your perimeter, fully air-gapped on-premise or self-hosted in your own cloud, so no code or data ever leaves your environment"*（§1.6.1）。**所以修出网边界是"补上一个信任负债、达到入场线"，不是"占据一个差异化位置"。** 真正的空位是 §1.6.2 那条：**证明"人"读懂了，而不是证明"代码"没坏。**

**此外，中国市场还有一条真实的采购动因**（调研取证）：《生成式人工智能服务管理暂行办法》（2023-08-15 生效）**把纯内部使用的企业场景排除在备案之外**——这给了"本地/私有化"一个具体的合规理由。**这与 Fieldguide 的默认 locale（zh-CN）正好对齐**，是本产品在地域上唯一有据可依的商业角度。⚠️ 但同份调研也指出行为侧的反证：**99% 的团队在用 AI 编码工具、15% 的公司明令禁止**——**"禁令不产生买家，只产生影子用户"**，所以这条不能当作现成需求。

### 2.5 飞轮（与现状的本质差别）

```
真检索（主干）→ 回答可信 + 出处可见 + 新鲜度可证（出口 C）→ 用户信任
   → 团队专家补充 why（策展）→ 体检针对策展出题（出口 A）
   → 错题 = 盲区数据 → 生成学习路径 → 掌握度提升 → 产出「理解证明」
   → 随 PR / 交接 / 导览包交付（出口 B）→ 传播
   → 更多真实仓库被索引 → 评测集扩张 → 检索继续变强 → 回到第一步
```

**现状是 12 个平行面板，任何一环都不为下一环提供输入。** 这就是「普通」的结构性根源，也是本方案与「再加功能」的根本区别。

**并且注意飞轮的落点变了**：它不再终止于"用户感觉自己读懂了"（不可证明、竞品也能宣称），而是终止于**一份可交付、可核验的理解证明**——这是本品类里唯一没人守、且我们用现成资产就能守住的位置。

| 评测基准 | 25 题 / 104 节点 / 3 种提问形式（`eval/datasets/pulsegate.qa.json`） | **两个口径要分清**：① **论文评测集**扩到 **60+**（`gap-analysis:311` 的既有计划：先 20 条高质量再扩到 60，因为节点级 ground truth 需人工标注、主观）——补中文自然语言与英文对照，加 HIS-Go（3656 节点）作大项目回归；② **体检题库**可达数百题，因为 locate/path 由图谱**程序化生成**、答案即节点，**不需要人工标注** |

**关键判断**：本方案的评测扩张成本极低，因为「题目答案 = 图谱节点」是结构性事实，不依赖人工标注。这同时把 C3（用户研究）从「另起炉灶」变成「产品自带的副产品」。

### 3.5 风险与缓解

| # | 风险 | 影响 | 缓解 |
|---|------|------|------|
| R1 | **供应商根本没有 embedding 端点**（实测：DeepSeek `/v1/embeddings` → 404，只有 2 个 chat 模型） | 向量通道对最常见的默认配置不可用 | ① **方案不得依赖 embedding**：归一化 + 符号通道作为主力（供应商无关）；② 向量通道仅在能力位为真时启用；③ 设置页显式提示「当前供应商不支持向量检索，可改用 SiliconFlow `BAAI/bge-m3` 等」 |

| R2 | **静态导览包无法脱离 Electron 运行期** | 出口 B 落空 | 本次已核实两处硬依赖：① Dashboard 经**特权协议** `ua-dashboard://` 加载（`dashboard.ts:24`），注释明确写着「ES module scripts / fetch 在 `ua-dashboard://` 下会被拒 → iframe 白屏」（`:20`）——**因此 `file://` 直接打开必然白屏，必须走本地静态服务**（`serve.cmd` 不是可选项而是必需项）；② UA CodeViewer 运行期 `fetch('/file-content.json?token=&path=')`（`:434`），该端点是 Electron handler 动态提供的 → 静态包必须**预物化** `file-content.json`。缓解：导出时只物化被 Tour / 架构叙事 / 热点引用的节点文件内容（受控体积），其余文件在只读模式下不提供查看。**风险等级：中→高**，故 W0 必须先 Spike；失败则降级为「结构化 Markdown + 图谱 JSON + 一键本地静态服务」 |
| R3 | 中文召回提升不达预期 | 旗舰卖点不成立 | **Spike 门禁**：先实测「词典改写 + 向量」在现有 25 题中文集上的真实提升，达阈值才继续 |
| R4 | 范围蔓延，回到「加功能」老路 | 重演本次困境 | §四「不做清单」+ 新功能必须挂进三条出口之一 |
| R5 | 体检被当成「考试」引发抵触 | 留存反降 | 定位为**体检**而非考试：不评分排名、可随时跳过、结果只给用户自己 |
| R6 | 上游 UA 变更导致向量 API 漂移 | 集成层返工 | 版本已 pin；集成层已是独立适配层（`ua/` 目录），漂移面可控 |
| R7 | Tour 被生成的学习路径覆盖 | 丢失既有内容 | 复用 `cross-tour.ts` 的**合并**语义（`gap-analysis §2.1 #4` 的历史教训） |

### 3.9 商业与定位可行性：**诚实结论（这一节的结论是"不要做产品，做工具/毕设/开源"）**

PM 若把「吸引用户」理解为「拉用户并收费」，那么本节给出的是**反对意见**——它是本次调研里最硬的一组市场事实：

| 事实 | 含义 |
|------|------|
| **CodeSee 卖的就是 Fieldguide 的话术**（codebase maps + interactive code tours + 页面标题 "Codebase onboarding"），标价 Community $0 / Business **$69 或 $29 每协作者每月**，**2024-05 被 GitKraken 收购**，`codesee.io` 与 `/pricing` 2026-07 起 404 | **"个人/团队的学习工作台"作为独立生意，公开市场上没有跑通先例**。⚠️ 但需诚实修正：`docs.codesee.io` 仍在线、无 EOL 公告，**GitKraken 至今在售 "Codemaps"**——所以是"品牌被关掉、能力被吸收"，**"正式日落"UNVERIFIED** |
| **graphify 的正确教训与直觉相反**：它不是"免费无公司的公益项目"，而是 **YC S26 的 Graphify Labs**——116k★ + 6.5M 下载 + Shopify/Datadog/JP Morgan/AmEx/Vanguard 生产使用，**付费层是"每个 PR 的形式化行为验证 + 全气隙部署"** | 本品类跑通的打法是 **OSS 楔子 → 付费企业验证层**。**"免费竞品多 ⇒ 没商业模式"是错误推论**；真正的问题是**对手已经用这个模式跑到了 Fieldguide 追不上的分发量** |
| CodeBoarding（同为架构视图）**把商业故事转向 PR review** | 架构视图**本身不产生收入** |
| **Understand by SciTools** 是唯一持久的付费桌面理解工具，**$100–120/月**，买家是**受监管 / 安全关键工程**，把"结构性理解"当作**合规产物**；⚠️ **它已上线 "Onboard"**（"AI-powered code understanding… understand unfamiliar codebases"） | 本品类唯一被证明的付费点：**合规 / 审计**——而这条赛道的在位者**刚刚走进 Fieldguide 的车道** |
| **个人开发者预算薄弱但非为零**（开发工具侧锚定 $0，付费替代 $9.99/月） | 调研原话：**"这是 Fieldguide 最危险的预算目标"**。⚠️ 关于"学习付费"的证据是**混合**的，且**不能只看一家**：Coursera FY2025 10-K（accession `0001651562-26-000015`，**已独立从 EDGAR 核实**）显示消费者占 **66.3%（$502.2M）**且增速快于企业；**但 Udemy 的 Enterprise 占收入 66%（从 58% 上升）而消费者同比 −9%**，**Pluralsight 是 87.7% 企业**（消费者 18.9%→12.3%）。→ **企业技能培训明确是 B2B；消费级市场平台则不是。不能从任何单独一家做推广。** 对本文可辩护的结论只有一句：**在"开发者理解工具"这一细分，个人付费锚定 $0**。⚠️ **核实状态**：Coursera 由调研者本人从 EDGAR 复核；**Udemy 与 Pluralsight 的数字仍是"照录"，因其复核请求被 `sec.gov` 403 拒绝——对外发布前需人工抽查。** |
| 本品类的创业资金集中在 **AI 代码评审**（CodeRabbit **$143M C 轮 / $1.5B 估值**，2026-08-12，厂商自发布；Cognition **>$2B / $48B 估值**） | 不要指望"理解工具"这个赛道本身拿到资金 |

**因此本方案的定位主张是**：

1. **默认形态：开源工具 / 毕设 / 作品集**（`NOTICE.md` 已是 MIT）。**不要为"个人学习付费"写商业计划**——在开发者理解工具这一细分，它的锚是 0。
2. **⭐ 唯一值得下注的位置：证明"人"读懂了变更，而不是证明"代码"没坏**（§1.6.2）。理由：Graphify Labs 的企业层证明的是**行为等价性**（机器验证），而 Understand 的合规买家买的是**人对系统的理解**——两者不是同一命题。出口 A 的体检分数（Lacy 式）+ 出口 C 的出处与新鲜度证明，组合起来正是**"谁在什么 commit 上证明了理解什么"**的合规式产物。**这是本次调研中唯一既未被占据、又与 Fieldguide 现成资产（`eval/` 测量仪器 + 图谱 + Obsidian 所有权模型）吻合的位置。** ⚠️ 但这条路的销售是**自上而下的报价式**（调研：comprehension 类产品 "top-down on quotes, not self-serve"），与单人项目资源不匹配，**应作为"未来工作"而非本轮目标**。
3. **本轮真正该争取的指标不是用户数，而是"一个可证明的数字"**：体检分数（对标 Lacy 的 83% vs 57%）或检索指标（对标本品类的检索瓶颈）。**在一个没人能证明自家结论正确的品类里，"能证明"本身就是位置。**
4. **⚠️ 但必须承认：学习闭环这个楔子有反证。** 免费的 `ai-study-kit`（**0★**）**已经实现了 SRS 复习队列 + 面试准备**，`magic-memory` 3★、`GoCard` 58★——**同类想法在免费侧已存在且毫无牵引力**，且调研的证据档案**找不到任何需求证据**。因此**它不是护城河，是一个必须用最小成本去证伪的假设**（见 §3.6 的两周验证：不要先投 21 人日的 P1，先用两周做真实用户测试）。
5. **⭐ 相对的优先级修正（§1.8）**：**"锚定 + 稳定 + 谁在何时确认"这一组，比学习闭环更值得先做**——它是**确定性**目标（可验证，不需用户研究），**直接回应竞品自认的缺陷**（DeepWiki 作者承认把核对工作交给读者），且**没有 0★ 墓地**。因此本轮资源顺序建议为：**P0（缺陷修复）→ 出口 C 的稳定/出处/新鲜度 → 两周证伪学习闭环 → 出口 A → 出口 B**。

**⭐ 钱在这个品类里实际怎么走（调研的收口结论，比"不能做"更有用）**：

> **本品类的钱是作为"企业平台/工具预算"流动的，按座位（约 $15–40）卖给工程负责人——不是一个学习类产品。**

配套的四条可操作含义：

| 事实 | 含义 |
|------|------|
| 工程负责人把**"工具预算不足"（24%）排在"培训不足"（14%）之前** | 这是**工具预算行**，不是 L&D（学习与发展）预算行——**去 Engineering 要钱，不要去 HR** |
| **"价格过高"是个人项目类工具的第一劝退因素** | 免费层必须是真免费（Fieldguide 本就开源，符合） |
| **面试准备是"消费者发起、雇主报销"**（ByteByteGo 创始人：*"Many subscribers use their company's learning budget"*） | 表面消费级、实为**受治理的预算**——个人版只当漏斗 |
| **没有任何分析机构发布本品类的美元 TAM**（RedMonk：*"Market size estimation is generally guesswork, and often hilariously wrong"*） | **任何 TAM 都必须自下而上搭**，不得引用现成数字 |

⚠️ **并且这不改变本节的核心结论**：上述是"钱怎么走"，不是"Fieldguide 现在能拿到钱"。拿到的前提是**先有一个可证明的数字**（§3.9.3）与**一个企业愿意签字的东西**（§1.8 的稳定 + 可确认）。**单人项目在 10 周内做不到后者**——所以本轮仍应定位为开源工具 + 一个可证明的数字。

> **⚠️ 最后一条诚实声明（调研的残留空白，不得省略）**：**付费意愿在本调研中从未被测量——所有需求信号都是"注意力"，不是"预算"**；Reddit 全程 403，定性基础偏 HN；且**没有任何具名西方企业公开说"因为政策禁止上云所以跑本地"**，因此**"企业对离线/气隙的付费意愿"是推断，不是已核实事实**。任何把本节的数字直接当作商业计划的用法，都超出了证据范围。

> **对 PM 的最终答复**：这个项目**不该**用"加功能吸引用户"来解决——它的五个支柱都已被免费产品覆盖（§1.6），它选的品类作为独立生意已被证伪（本节），它最自然的差异化位置（气隙验证）已被一家 YC 公司用 100k★ 分发量占住，而**它的分发策略本身已被 Sourcegraph 试过并公开关停**（§1.10）。**在"吸引大量用户"这个目标上，本方案的可行性结论是：不成立。**
> **成立的是一条有先例支撑的路（§1.10 的 Bruno 机制）**：**移除一项已被记录的强加，而不是增加功能**。Fieldguide 手上的强加清单是现成的——**无法核验的 AI 解释**（出口 C 移除它）、**默认上传代码库 / 默认遥测 / 强制账号**（出网边界与开源默认移除它们）。Bruno 用同样的机制从 Postman 手里赢到 600k+ MAU，而**它的赢法不是"功能更多"**。
> **成立的三件事**：① 修掉两处真实缺陷（假语义搜索 / 能力协商），6 人日——损害的是产品可信度本身；② 优先做**"锚定 + 稳定 + 可确认"**（确定性、无 0★ 墓地、直击竞品自认缺陷）；③ 学习闭环若要做，**先两周证伪**。**若必须选一个对外位置，选"证明人读懂了、且这条结论稳定到可以签字"**——它同时满足"唯一空着"与"移除一项强加"两个条件。

## 五、需要 PM / 决策者拍板的六件事

1. **确认评价标准**：是「功能点数量与体系完整度」，还是「用户是否愿意持续打开并把一个可证明的数字带走」？本方案服务后者。若前者，请明确——两条路的投入产出完全不同（见 §3.8）。

   - `doc-index.md:94` 把「语义代码搜索」记为已交付，实现是 Fuse.js（中文召回 12.8%）；

3b. **确认验收指标口径（§1.10 的指标纪律）**：**是否同意禁用"下载量 / star 数 / 试用数"作为验收指标？** Sourcegraph App 用的正是这三个，发布仅 1 分 HN、随后 Cody Free/Pro 被删。本方案只承认理解类（A9/A10）与检索类（A1–A4）指标。若 PM 坚持用用户增长验收，即等于选择重走已关停的先例。
4. **确认定位（§1.5 / §1.6 / §1.7 / §1.8 / §1.9）**：这是本次最重要的拍板项，且**调研结论与现有文档冲突**：
   - 文档把差异化定为「概念桥接 + 跨源 Agent」（`doc-index.md:15`，**不可漂移**）；

   - **"气隙 / 本地优先"已被 graphify 的 YC 母公司用同样措辞占住**，不再是空位（§1.6.1）；
   - 学习闭环（间隔重复 + 掌握度 + 体检）**未被商业工具占据**，有 Lacy/FSE 2026 的**唯一实验支撑**（83% vs 57%），但**无需求证据、免费侧已有 0★ 先例、且 SRS 的变现天花板只有 $6–10/月**（§1.8）。

   **建议把对外主张改为「证明你读懂了 agent 写了什么，再合并」，并明确落在"证明人读懂了"而不是"证明代码没坏"（§1.6.2），同时把"稳定 + 谁在何时确认"作为技术承重点（§1.8）**——理由有四条独立证据：
   - 痛点侧："几乎对但不对" 66%、缺代码库上下文 64.6%、不信任输出 66.2%；
   - **理解是写的 2 倍痛且连续两年稳定**（JetBrains 微观数据重算：31.6% vs 15.6%（2025）、28.6% vs 13.8%（2024）；**出处与偏差限定见 §1.9**——DevEco 2024/2025 `RawData.zip`，行数与公布样本量一致，Goldfarb & Idnani 加权，2023 微观数据 403；JetBrains 已按 ×0.9 下调自身用户占比但**仍有残留偏向，故只用方向性**）；
   - **开发者明确不愿把"理解"交给 AI**（42.9% 自己做 vs 34.4% 愿委派）——**这是"给人用的理解产品"最直接的需求侧证据**（§1.9）；
   - **人类评审才是约束**（NBER，50 万+ 开发者：提交 +240% 但发布仅 +30%）；
   且该主张**绕开 DORA 对"文档→新人 ramp"的 null 结果**。⚠️ 此项触及 `doc-index.md` §一「产品一句话（**不可漂移**）」，**需正式决议，架构不能单方面改**。
5. **确认是否接受"这一轮不做商业计划"（§3.9）**：CodeSee 以同样话术标价 $29–69 仍未作为独立生意活下来（品牌已关、能力被 GitKraken 吸收为 "Codemaps"）；本品类唯一的规模化商业成功是 **graphify = OSS 楔子 + 付费企业验证层（YC S26）**，而那需要 Fieldguide 追不上的分发量。**建议本轮定位为"开源工具 + 一个可证明的数字"，商业化写入"未来工作"。** 若 PM 的 KPI 是"拉新与付费"，本方案**不解决**该 KPI——应明确告知，而不是用功能数量去凑。
6. **⚠️ 确认是否接受"先花两周证伪，而不是先花 21 人日建设"这一顺序**：学习闭环是唯一未被占据的层，但（a）调研找不到需求证据，（b）`ai-study-kit`（**0★**）已经实现了 SRS 队列 + 面试准备却毫无牵引力，（c）Lacy 本身是单公司、未复现。**因此建议把 P1 的体检/策展（21 人日）排在一次真实用户的可用性测试（N=3–5，两周内）之后**——先证伪再投入。若 PM 不同意这个顺序，就是在为一个无需求证据的功能下注，应记录该风险。

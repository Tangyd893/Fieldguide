# 用户研究设计与分析方案（C3）

> 目标：验证「Fieldguide 是否真的帮助开发者更快读懂陌生仓库」——为论文提供**可复现的实验设计与统计口径**。
> 计分代码：`src/main/eval/usability.ts`（SUS + 任务指标），单测见同目录 `__tests__/usability.test.ts`。
> 本文件只提供**工具与协议**；数据必须由真实参与者产生，代码里不预置任何"模拟结果"。

---

## 一、研究问题

| 编号 | 问题 | 对应指标 |
|------|------|----------|
| RQ1 | 与「IDE + 通用聊天」相比，Fieldguide 能否缩短读懂一个陌生项目的任务时间？ | 任务耗时（均值/中位数）、完成率 |
| RQ2 | 能否提升对项目结构的理解准确度？ | 正确率、自评理解度（0–5）、后测题得分 |
| RQ3 | 可用性是否达到可接受水平？ | SUS 总分与两个分量表 |
| RQ4 | 学习闭环（进度/笔记/复习）是否被真实使用并有帮助？ | 使用日志（见 §五）、主观反馈 |

---

## 二、设计

**被试内设计（within-subject）**，每位参与者完成两条**等难度**任务序列，条件随机平衡（拉丁方）：

- **条件 A（对照）**：IDE（VS Code / GoLand）+ 通用 AI 聊天（ChatGPT 等），自行探索。
- **条件 B（实验）**：Fieldguide（图谱 + 导览 + 教练 + 洞察面板）。

选择被试内而不是组间的原因：样本量小（n≈8–12）时组间差异会被个体差异淹没；同一人做两种条件能显著提高统计效力。**代价**是学习效应与疲劳效应，用「随机顺序 + 两条任务序列等难度 + 每条件间 5 分钟休息」控制。

### 任务素材

| 序列 | 仓库 | 说明 |
|------|------|------|
| S1 | 内置 Demo `pulsegate`（104 节点 / 9 分层 / 15 个源文件） | 规模小，用来跑通流程与暖身 |
| S2 | `HIS-Go`（3656 节点，真实业务系统）或另一个千级以上节点、参与者**从未见过**的开源仓库 | 主实验，避免熟悉度干扰 |

> 每个参与者只使用其中一条序列的另一条件对应仓库——**两条序列必须难度可比**：建议各准备一个「小」一个「大」，并在分析时把序列作为协变量。

## 三、任务脚本（每条件 30 分钟上限）

| # | 任务 | 成功标准（客观） | 记录 |
|---|------|------------------|------|
| T1 | 说出这个项目的**入口**与**主数据流** | 能指出真实入口文件，并按顺序说出至少 3 个环节 | 完成与否 + 正确与否 + 耗时 |
| T2 | 找到「X 功能」的实现位置（X 由主试指定，如鉴权 / 限流 / 入库） | 打开的文件属于标注的正确文件集合 | 同上 |
| T3 | 回答一个**跨模块**问题（A 怎么调到 B） | 能说出中间环节（≥2 个） | 同上 |
| T4 | 列出「下一步应精读的 3 个文件」并说明理由 | 3 个文件中 ≥2 个属于高扇入/核心文件 | 同上 |
| T5（仅条件 B） | 用笔记/进度标记该模块，生成一次复习卡片 | 截图或日志证明产物已生成 | 可用性观察 |

主试记录到 `TaskRecord`：`{ participantId, taskId, seconds, completed, correct, understanding, notes }`，用 `summarizeTasks()` 汇总。

## 四、量表

### 4.1 SUS（每位参与者每条件各一次）

10 题、5 点 Likert（1 完全不同意 … 5 完全同意），题面见 `SUS_ITEMS`（中英双语，按参与者语言选择）。

计分：奇数题 `score − 1`、偶数题 `5 − score`，求和后 ×2.5 → 0–100。
- 分量表：可用性 = 题 1/2/3/5/6/7/9；易学性 = 题 4/10（题 8 只计入总分，这是 Brooke 原始划分）。
- 形容词分级：≥85 best、≥72 excellent、≥68 good、≥51 ok、≥25 poor、其余 worst。
- **注意**：所有题都给同一分（例如全填 4）会得到 50 分——量表本身如此设计，分析时要留意敷衍作答。

问卷不够 10 题一律记为无效并**排除**（`summarizeStudy()` 会返回 `excluded` 计数，论文里必须报告剔除数量）。

### 4.2 主观反馈（开放题）

1. 哪个功能最有帮助？为什么？
2. 哪一步让你卡住或困惑？
3. 如果只能保留一个功能，你会保留哪个？
4. 你会在真实工作中用它吗？什么场景？

### 4.3 后测理解题（可选，用于 RQ2 的客观分）

围绕所读仓库准备 8 道选择题/简答题（入口、分层、数据流、依赖方向、风险点各 1–2 题），满分 8；两条件各用**难度配对的等长版本**。

## 五、使用日志（RQ4）

条件 B 的客观使用数据从应用侧采集（本地、经同意后导出）：

| 数据 | 来源 | 用途 |
|------|------|------|
| 面板切换次数 / 停留时长 | 壳层事件（可临时加埋点） | 哪些面板真被用 |
| 打开的节点 / 文件数 | `graph:getNode`、`file:read` | 探索广度 |
| 笔记条数、进度标记数 | `code_notes`、`learn_progress` | 学习闭环是否被使用 |
| 复习完成数与记住率 | `review_logs` / `computeReviewStats()` | 复习环节是否有效 |
| 教练提问次数与引用点击次数 | `chat:send`、引用 chip 点击 | Agent 是否被信任 |

> 隐私：日志留在本地，导出需参与者明确同意；论文中只报告聚合值。

## 六、分析方案

1. **描述统计**：SUS 均值 ± 95% CI、两个分量表、任务耗时（均值与中位数并列——耗时通常右偏）、完成率/正确率。
2. **假设检验**：条件 A/B 的连续指标用**配对 t 检验**（不满足正态性时用 Wilcoxon 符号秩检验）；比例指标用 McNemar 检验。报告效应量（Cohen's d 或 r），不要只报 p 值。
3. **相关性**：SUS 与任务耗时/理解得分的相关性（Spearman），用于讨论"好用"与"有效"的关系。
4. **定性**：开放题做主题编码（两名编码者独立编码，报告一致性）。
5. **样本量与其局限**：n=8–12 属**探索性**研究，置信区间会很宽；论文中明确写"效应量仅作方向性参考，不作为确证性结论"。这是诚实且常见做法。
6. **偏倚控制**：顺序平衡、等难度任务、同一主试同一脚本、任务前不看代码、条件间休息、SUS 在**两条件都做完后一起填**（避免对比暗示）。

## 七、执行清单

- [ ] 招募 n=8–12 名有 2 年以上经验、**未读过目标仓库**的开发者；签署知情同意（记录/录屏需单独同意）
- [ ] 准备两套等难度任务序列与答题卡；预跑 1 名试测者（不计入数据）校准时长
- [ ] 演示前清理环境（同一台机器或同规格机器；关闭通知）
- [ ] 逐人执行、逐条记录 `TaskRecord` 与 SUS 原始作答
- [ ] 用 `scoreSus` / `summarizeStudy` / `summarizeTasks` 生成表格，原始作答一并归档
- [ ] 报告时写明：样本量、剔除的无效问卷、顺序、是否使用同一仓库、局限性
